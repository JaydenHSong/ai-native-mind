# Vibe Coding Antipatterns

## Easy Read

**In a Nutshell**: **Vibe Coding** represents an engineering attitude of programmatically accepting AI-generated code without checking its underlying logic because "it feels okay at first glance." This page outlines what happens to **security, data privacy, and maintenance** when codebases are built this way. Treat this document as a helpful **diagnostic checklist**, not a finger-wagging sermon.

| Term | Explanation |
|------|------|
| **Antipattern** | A common software habit that appears intuitive but leads to failure in production |
| **API Key** | A secret token used to authenticate calls to external APIs—leaking this exposes your systems and wallet |
| **Maintenance** | The continuous effort required to keep software running, updated, and secure after release |

## One-Line Definition

A diagnostic catalog detailing the core failure patterns of uncritical acceptance of AI-generated code (Vibe Coding) alongside actionable mitigation blueprints.

## 2026 Industry Telemetry

- **Up to 45%** of AI-generated code snippets contain active security vulnerabilities.
- A massive security breach in early 2026 traced to a vibe-coded startup exposed **over 1.5 million API keys and 35,000 corporate emails** via raw model outputs.
- Systems architects compare unconstrained vibe coding to the structural management failures of the Challenger disaster.

## The 7 Core Vibe Coding Antipatterns

### 1. The Happy Path Assumption
Models write excellent code for optimistic execution scenarios, but fall short on exception handling:
- ✅ Normal input $\to$ Executed successfully.
- ❌ Boundary/Edge cases $\to$ Ignored.
- ❌ Error responses $\to$ Unhandled.
- ❌ Anomalous payloads $\to$ App crashes.
*High-Risk Targets*: Authentication modules, transaction/billing processors, cryptographic routes, and user input validation blocks.

### 2. Security Blindness
Common security defects regularly generated by models:
- Storing passwords in plain text.
- Hardcoding API credentials directly inside code files.
- Susceptibility to SQL Injection.
- XSS and CSRF vulnerabilities.
- Absence of API rate limiting.

### 3. Happy Diff, Sad System
- The model outputs a clean, atomic diff block.
- The developer accepts the diff without auditing how it impacts the broader system architecture.
- A seemingly isolated update **silently breaks a downstream dependency**.

### 4. Architectural Decay
The cumulative outcome of multiple unconstrained vibe coding sessions:
- The codebase evolves without conscious architectural intent.
- Files become tightly coupled and disorganized.
- Maintenance becomes impossible.
- **The codebase decays into an unmaintainable "spaghetti" architecture.**

### 5. Context Amnesia
- The model's context window cannot hold the entire repository architecture in memory.
- The model invents new ways to solve problems that are already solved in the codebase.
- Duplicate code blocks explode, and APIs become inconsistent.

### 6. The Prompt Gambler
- The developer tweaks the prompt iteratively without understanding the underlying code errors: *"Let's try this prompt, maybe it will work."*
- Resolving compiler errors by trial-and-error instead of logical analysis.
- The developer has no idea if the bug is actually fixed. They simply celebrate because: *"This time, the terminal did not output an error."*

### 7. Deployment Roulette
- Pushing updates straight to production without running local test suites.
- Blind trust in the model's assertion: *"I have verified the code, it is safe to deploy."*
- The application crashes in production.

## Red Flags Diagnostic Checklist

### Are You Trapped in the Vibe Coding Loop?

- [ ] You frequently inspect files and ask: *"Who wrote this function and what does it do?"*
- [ ] During debugging sessions, you ask the model to explain your own codebase to you.
- [ ] Unexplained runtime bugs continually crop up in production.
- [ ] The model writes your unit tests, and you verify them solely by checking if they "PASS."
- [ ] The same utility function is implemented differently across three separate files.
- [ ] You let the model generate Git commit summaries and PR descriptions without reading them.
- [ ] You paste error messages straight into the prompt window without reading the stack trace yourself.

## Why Solo Developers Face Extreme Risk

- **Absence of Peer Review**: There are no human colleagues to double-check code. If both you and the model miss a race condition, it goes straight to production.
- **Double-Blind Domain Ignorance**: The model generates a flawed domain model, and the developer lacks the domain expertise to catch the error.
- **Velocity Pressure**: The temptation to "ship fast" overrides the discipline of running manual checks, accumulating massive [[concepts/cognitive-debt|Cognitive Debt]].

---

## Safe Vibe Coding Boundaries

### ✅ Low-Risk Scenarios (Go Ahead!)
- Rapid MVP prototyping and greenfield exploration.
- Hackathons.
- Internal-use utility scripts.
- Sandbox learning and prototyping.
- Personal, low-traffic hobby projects.

### ❌ High-Risk Scenarios (Avoid Vibe Coding)
- Enterprise production backends.
- Transactional financial, medical, or legal applications.
- Processes handling sensitive PII data.
- Core authentication and authorization modules.
- Complex distributed databases.

---

## Essential Guardrails

1. **Mandatory Code Reviews**: Read every line of code generated by the model before committing.
2. **Automated Unit Tests**: Block merges if the local test suite fails.
3. **Static Security Scans**: Run automated SAST/DAST security checkers in your CI/CD pipeline.
4. **Specification-Driven Workflows**: Verify implementations against explicit design documents.
5. **Architectural Ownership**: Humans must own the high-level system design; agents should only implement the details.
6. **Incremental Commits**: Commit code in small, atomic changesets to keep modifications understandable.

## From Vibe Coding to Agentic Engineering

Andrej Karpathy details the maturity trajectory of AI-assisted developers:

```
VIBE CODING   ──→ Simply accepts model outputs without verification
     │
     ▼
AGENTIC ENG.  ──→ Leverages formal harness guards, tests, and active human oversight
```

Transitioning from "vibing" to professional **Agentic Engineering** requires replacing blind trust with structured validation harnesses. Refer to [[concepts/agentic-engineering|Agentic Engineering]].
