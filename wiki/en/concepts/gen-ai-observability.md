# GenAI and Agent Observability (OpenTelemetry)

## Easy Read

**Analogy**: As an application runs for extended durations, recording "where it stopped and who called what" like a **black box flight recorder** is observability. **OpenTelemetry (OTel)** is an open standard designed to align **labeling rules** so that different tools do not speak entirely separate dialects. Among these, **GenAI semantic conventions** are standard labels tailored specifically for AI concepts, such as "model invocations" and "tool calls."

| Term | Explanation |
|------|------|
| **Trace** | A bundle of **footprints** representing a single request moving through a system |
| **Span** | A single footprint in a trace (e.g., a single model invocation) |
| **Metrics & Logs** | Numerical data (count, latency, cost) and text logs |

## One-Line Definition

An open, vendor-neutral approach to observing **traces, metrics, and logs** generated by Generative AI and agent applications, aligned directly with the **OpenTelemetry (OTel) GenAI semantic conventions**.

## Why It Trashes "Just Plain Logs"

- Because agents are **non-deterministic**, telemetry data serves not just for incident response, but also feeds directly into the **quality and evaluation feedback loop**.
- If every framework uses a different proprietary log format, unifying cost, latency, and A/B test analysis becomes next to **impossible**.

## Layers of OpenTelemetry Standardization

| Layer | Description |
|----|------|
| **GenAI Semantic Conventions** | Standardizing **attribute and span names** for model calls, tool usage, and vector DB queries. [Official Spec Docs](https://opentelemetry.io/docs/specs/semconv/gen-ai/) |
| **Agent Application Conventions** | Standardizing observations of individual agent entities. Drafts and SIG discussions in progress. |
| **Agent Framework Conventions** | Standardizing LangGraph, CrewAI, AutoGen, and other framework surfaces, with vendor extensions. |

Because specs **evolve rapidly**, locking down the specific version and experimental flags (e.g., stability opt-in) in the release notes is an essential part of harness engineering.

## Two Instrumental Approaches (Summary)

1. **Framework-Baked-In Instrumentation** — Easiest to adopt, but the responsibility of matching upstream OTel conventions and versions lies entirely on the framework vendor.
2. **External OTel Instrumentation Packages** — Highly flexible, though prone to version matching and fragmentation risks.

Regardless of the approach, **aligning strictly with the Agent Framework Semantic Conventions** is emphasized as the prerequisite for interoperability.

### Two-Way Decision Guide

Refining trade-offs discussed in the official OTel blog [AI Agent Observability — Evolving Standards and Best Practices (Liu & Solomon, 2025-03-06)](https://opentelemetry.io/blog/2025/ai-agent-observability/):

| Dimension | Baked-In (e.g., CrewAI) | External OTel Packages (Traceloop, Langtrace, [`instrumentation-genai`](https://github.com/open-telemetry/opentelemetry-python-contrib/tree/main/instrumentation-genai)) |
|------|------|------|
| User Default | ON by default | Must be added manually |
| Telemetry of New Features | Fast (baked into framework) | Dependent on separate package update cycles |
| Bloat | Overhead for users not using APM | Zero |
| OTel Version Lock-In | High risk (framework must keep up) | Resolved by updating individual packages |
| Advanced Flexibility | Low | High |
| OTel Spec Adherence | Framework's responsibility | Open to public community review |

**Best Practices for Baked-In Approaches**: Provide toggles to turn telemetry off, avoid conflicts with external packages, and register in the [OTel registry](https://opentelemetry.io/ecosystem/registry/).

**Long-Term Vector**: Migrating external instrumentation to official OTel repositories (e.g., Traceloop's [donation proposal](https://github.com/open-telemetry/community/issues/2571)) is highly recommended.

### AI Agent Application ≠ AI Agent Framework

A critical distinction highlighted in OTel documentation:
- **AI Agent Application**: An individual AI entity autonomously executing a specific domain task.
- **AI Agent Framework**: The software infrastructure used to build, manage, and deploy agents—e.g., IBM Bee AI, wxFlow, CrewAI, AutoGen, Semantic Kernel, LangGraph, PydanticAI.

Telemetry semantic conventions are split into **app conventions** and **framework conventions** ([app issue #1732](https://github.com/open-telemetry/semantic-conventions/issues/1732), [framework issue #1530](https://github.com/open-telemetry/semantic-conventions/issues/1530)). Frameworks can layer their proprietary vendor attributes atop standard OTel layers.

Furthermore, telemetry is not just a passive dashboard; it is **active input for the evaluation loop**. Joining a trace's `trace_id` and session with evaluation datasets enables unified analysis of cost, latency, and quality regressions, even across heterogeneous frameworks.

### 2026-05-03 Update — Datadog State of AI Engineering 2026 (1,000+ Customer Traces)

The [Datadog State of AI Engineering 2026](https://www.datadoghq.com/state-of-ai-engineering/) report provides empirical data from **1,000+ production customer LLM traces**, reinforcing that observability is a hard requirement.

| Operational Fact | Metric | Strategic Implication |
|------|------|------|
| Model Diversification | **70%+ of organizations run 3+ models**, share of 6+ models nearly doubled | Model gateways are now standard infrastructure |
| Legacy Model Preservation | GPT-4o **22%**, Sonnet 3.5/4.5 **19%** (as of 2026-03) | "Model debt" poses significant governance challenges |
| Framework Adoption | Surged from **9% to 18%** in 1 year, average services doubled | Architectural sprawl requires deep telemetry |
| System Prompt Footprint | Comprises **69%** of input tokens | System prompts represent the primary cost driver of scaffolded agents |
| Prompt Caching Utilization | Only **28%** of cached-reads utilized in supported models | [[patterns/prompt-caching|Prompt caching]] remains the single largest unharvested ROI |
| Top Failure Mode | Rate limits represent **30~60%** of all errors | Backpressure, budgets, and queue gating are top-tier safety priorities |
| Monolithic Agents | **59% contain a single call**, 3+ calls represent **18%** | True multi-agent swarms are early in adoption, and require trace propagation once scaled |

*Key Takeaway* (Vercel's Guillermo Rauch): "The next wave of agent failures will come not from what teams cannot build, but from what teams cannot observe." Unifying **GenAI semconv → traces → evaluation loops** is not a luxury; it is the cornerstone of reliability infrastructure.

Connecting to Operational Guidelines:
- **Rate limiting as the top failure mode** reinforces the cancellation and timeout policies of [[patterns/agent-server-harness]]. Backpressure handling is mandatory.
- **69% system prompts vs. 28% cache utilization** shows that the dramatic cost reductions of [[patterns/prompt-caching]] remain widely unharvested. Design prompt layouts to maximize cache prefix reuse.
- **Model debt** represents a new form of [[concepts/cognitive-debt]]. Establish strict model retirement gates in your operations playbook.

## 2026-05-06 Update — Agent Design-Level Observability (AHE)

[Agentic Harness Engineering: Observability-Driven Automatic Evolution of Coding-Agent Harnesses (arXiv 2604.25850)](https://arxiv.org/abs/2604.25850) separates **infrastructure-level observability (OTel/Datadog)** from **agent design-level observability**. To prevent automated harness evolution from collapsing under trial-and-error noise, all three pillars are required:

| Pillar | Infrastructure Level (OTel/APM) | Agent Design Level (AHE Requirement) |
|--------|---------------------------|------------------------------------|
| **Component Observability** | Services & process topologies | **Editable components (prompts, tools, evaluation rules) isolated at file-level**, fully revertible |
| **Experience Observability** | Raw logs & traces | Distilling million-token trajectories into a **layered drill-down evidence corpus** consumable by the evolution agent |
| **Decision Observability** | Deployment & deployment logs | Pair every edit with a **self-declared prediction**, validated as a **falsifiable contract** against next-round task results |

*Results*: Over 10 iterations of AHE, Terminal-Bench 2 pass@1 scores rose from **69.7% to 77.0%**, outperforming handcrafted SOTA harnesses (Codex-CLI at 71.9%) and ACE/TF-GRPO. **Well-designed design-level observability enables automated evolution to beat handcrafted SOTA**.

### Immediate Applications for Our Workspace
- Currently, our **Sensors (lint + frontmatter validation)** satisfy only component observability. We lack **decision observability**. Adding a single `self-declared prediction` field to our ingest logs specifying *what this edit is hypothesized to fix* establishes a falsifiable contract.
- Maintain harness components (CLAUDE.md, templates/, prompt snippets, evaluation rules) as **modular, small files rather than a single monolithic document** to ensure component observability and attribution survive.

### Pairing with Datadog Metrics
While the **Datadog State of AI Engineering** section highlights **infrastructure-level operational debt** (rate limits, uncached prompt waste), AHE addresses **agent design-level observability deficits** (inability to attribute why an edit improved outcomes). They are two sides of the same coin: "what you cannot observe, you cannot fix."

## 2026-05-24 Update — ActiveGraph: Transitioning from Logging Logs to Logs as the Runtime

[The Log is the Agent](https://arxiv.org/abs/2605.21997) / ActiveGraph (2026-05-21) pushes observability to its logical limit. Historically, high-quality observability meant **retaining high-fidelity traces post-execution**. ActiveGraph proposes a radical alternative:
> **The log is not a post-hoc record; it can serve as the central, active data structure of the agent runtime.**

### 1) Traceability as the Execution Model
ActiveGraph's core intuition aligns directly with event-sourced systems:
- Action executions and state transitions are appended to an immutable, append-only log.
- Replays, forks, and audits are executed directly against this log.
- Observability and execution share the identical substrate rather than operating as separate features.

It moves beyond "observability of agents" to **"agents executing directly atop active observability structures."**

### 2) Importance for Observability Documentation
Tracing the adjacent evolution across this wiki clarifies the landscape:
- **OTel / Datadog**: Standardized telemetry surfaces to track active runs.
- **AHE**: Decision observability linking harness edits to functional outcomes.
- **HarnessAudit / ProcBench**: Post-hoc analysis auditing trajectories and interpreting processes.
- **ActiveGraph**: Event-sourced log as a branchable runtime substrate.

ActiveGraph elevates observability from passive diagnostics to the core design principles of **state management, replayability, and auditability**.

### 3) Redrawing the 2026 Observability Stack

| Layer | Key Objective | Primary Reference |
|---|---|---|
| **Telemetry Standard** | What attributes to record and under what names? | OTel GenAI semconv |
| **Operational Diagnosis** | How to track cost, latency, and failure distributions? | Datadog APM |
| **Design Observability** | What architectural edits caused what downstream effects? | AHE Framework |
| **Runtime Auditability** | Can we replay, branch, and formally audit execution histories? | **ActiveGraph** |

Observability shifts from simple data harvesting to a **runtime architecture engineered for forkable execution history**.

### 4) 3 ROI Actions for Solo Developers
1. Design critical agent workflows around **replayability benchmarks** rather than simple flat logs.
2. Prioritize **append-only event sequences** over mutable state stores to ensure robust debugging and auditing.
3. When structuring sub-agents, evaluate whether state and telemetry can be merged into a **unified history substrate** rather than kept in isolated databases.

## Minimal Practical Checklist

- [ ] Consistently apply **request metadata** (model ID, token aggregation/count policies) to all model call spans.
- [ ] Isolate tool and MCP invocations into **separate child spans**.
- [ ] Enforce mask-at-source masking rules to prevent raw PII from reaching span attributes.
- [ ] **Pin specific versions** of the OTel SDK and GenAI semantic conventions in dependencies.
