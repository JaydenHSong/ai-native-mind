# 2026-05-22 Learning Journal — code substrate · memory scale boundary · benchmark disclosure

## How to read this page (30 seconds)

Today's three papers cover different topics, but they can be summarized in one line.

> **Agent engineering is increasingly moving toward asking not "what did the model do," but "what code substrate was it operating on, how large can memory grow before it stops being usable, and how much of the execution context behind benchmark results was actually disclosed?"**

- [[concepts/harness-engineering|Harness Engineering]]: the view of code as not just output but a runtime substrate became much clearer.
- [[concepts/ai-memory-systems|AI Memory Systems]]: memory should be evaluated not only by retrieval accuracy but by whether it keeps usable evidence available **as scale grows**.
- [[concepts/llm-evaluation|LLM Evaluation]]: before reading a benchmark score, we should audit **run disclosure quality**.

---

## 1. The three papers collected today

### 1-A. Code as Agent Harness

**One line**: "Code is both an artifact produced by the agent and the harness through which the agent thinks, acts, and verifies."

- framing:
  - code is not just output; it is an **operational substrate**
  - it connects reasoning / action / environment modeling / execution-based verification
- 3-layer survey frame:
  1. **harness interface**
  2. **harness mechanisms** (planning / memory / tool use / feedback control)
  3. **multi-agent scaling** (shared artifact / review / verification)
- key implications:
  - it encourages viewing planning, memory, and tool use not as separate features but as **code-backed harness mechanisms**.
  - it shifts the medium of multi-agent coordination away from **messages** and more toward **shared files / diffs / test harnesses**.

### 1-B. Scale-Conditioned Evaluation of Agent Memory

**One line**: "The real question for memory is not whether it can retrieve well right now, but whether it can keep surfacing the needed evidence within budget even as irrelevant sessions keep accumulating."

- problem setting:
  - task evidence is fixed for each query
  - only irrelevant sessions are added progressively
- 4 diagnostics:
  - **budget-compliant reliability**
  - **tail memory-call burden**
  - **failure-regime decomposition**
  - **usable-scale boundary**
- key findings:
  - **HippoRAG** stays within a two-call budget, but reliability drops by **16–20 percentage points** as irrelevant sessions increase
  - **LiCoMemory** depends more heavily on the agent; Qwen3-8B exceeds budget, while Qwen3-32B / 235B are relatively stable

### 1-C. Benchmark Disclosure Audit

**One line**: "Before benchmark scores, we should first measure how much a paper reveals about the harness and settings that produced those scores."

- audit schema, 5 fields:
  1. **benchmark identity**
  2. **harness specification**
  3. **inference settings**
  4. **cost reporting**
  5. **failure breakdown**
- pilot audit results:
  - **agent benchmark papers average 0.38 / 1.0**
  - **classical static benchmark papers average 0.66 / 1.0**
  - the biggest gaps are **cost** and **harness spec**
- key implication:
  - it explains why comparing results with the same model name often becomes blurry: **insufficient run disclosure**.

## 3. Connection points with existing knowledge

### 3-A. Code as Agent Harness unifies recent Harness Engineering threads into a higher-level frame

The recent flow had been fragmented like this.

- [[concepts/tool-use]] = capability object / runtime interface
- [[concepts/ai-memory-systems]] = belief / lifecycle / safety / enforcement
- [[concepts/llm-evaluation]] = spec truth / process quality / environment realism
- [[concepts/ai-orchestration]] = delegation / handoff / shared workflow

With today's Code as Agent Harness, all four lines can be grouped under the higher-level explanation of **code-backed harness mechanisms**.

### 3-B. Memory now adds the question of "scale boundary" on top of taxonomy

The previous memory taxonomy was roughly this.

- What do we believe, and how strongly? → BeliefMem
- When do we compress or forget? → Human-Inspired Memory
- What must not be forgotten for safety? → MAGE
- How do we enforce that something is never lost? → ClawVM

Today's paper adds one more question.

- **How large can it grow while still remaining usable?** → Scale-Conditioned Evaluation

In other words, memory should be understood not only through structure and update rules but also through **growth-conditioned usability**.

### 3-C. Eval now needs not just quality metrics but disclosure quality too

The recent eval lineage has deepened like this.

- JRH = judge reliability
- ResearchArena / SpecBench = surface vs truth gap
- ProcBench / HarnessAudit = process controllability / trajectory audit
- WildClawBench = environment realism

With today's disclosure audit, a **run disclosure layer** now sits underneath all of them.

That means from now on it is not enough to record only "which benchmark was used"; meaningful comparison also requires recording:

- what scaffold was used
- which evaluator version was used
- how much it cost
- what the failure breakdown was

## 5. Key learnings

1. **Code can be both an artifact produced by the agent and the agent runtime itself.**
2. **Memory evaluation should ask more forcefully about usability under growth and noise than about retrieval accuracy alone.**
3. **The usable-scale boundary is an operational metric that reveals the real-world limits of a memory system.**
4. **Benchmark scores lose much of their interpretive power if read without harness / evaluator / cost / failure metadata.**
5. **Recent agent evaluation is thickening into a multi-layer structure: judge → disclosure → truth → process → environment.**
6. **Shared artifact design is central to multi-agent coordination and can be more load-bearing than simple role prompts.**

### 9-B. The real overlap this week was "repeating the same topic under different boundary names"

On the surface, this week's sources were scattered across memory, eval, orchestration, and security, but in practice they converged on questions of **boundary design** like the following.

- **memory boundary**: what is trusted and how much, when is it forgotten, how large can it grow while remaining usable, and how does runtime enforce that it is not lost
- **control boundary**: what gets auto-approved and what gets handed back to a human

- **evaluation boundary**: do we look only at scores, or also at process / control / disclosure

So the overlap was not severe enough to warrant deleting pages. The bigger issue was **different boundary questions being placed under the same names — memory, eval, orchestration — which created overlap at the framing level**.
