# 2026-05-20 Learning Journal — delegation substrate · privacy diagnostics · artifact-aware auto-research

## How to read this page (30 seconds)

Today’s three papers all converge on the same conclusion: **you cannot understand agents by surface success rate alone**.

> **A good agent evaluation does not stop at “was the outcome okay?” It also asks (1) who delegated to whom and why, (2) what should not have been said, and (3) whether there is a real artifact behind the document.**

- [[concepts/ai-orchestration|AI Orchestration]]: delegation can remain nearly invisible under quality-only scoring
- [[concepts/agent-supply-chain-security|Agent Supply Chain Security]]: privacy is not just a tool-permission issue but also an issue of **attribute leakage during conversation**
- [[concepts/llm-evaluation|LLM Evaluation]]: manuscript-only review can overestimate plausibility

---

## 1. Three papers collected today

### 1-A. DecisionBench

**One line**: “To tell whether a multi-agent system delegated well, you need routing fidelity, not just final accuracy.”

- Target: **emergent delegation in long-horizon workflows**
- Setup:
  - **GAIA / tau-bench / BFCL multi-turn**
  - **11 models / 7 vendor families**
  - `call_model` + optional `read_profile`
- Metrics:
  - quality
  - cost
  - latency
  - delegation rate
  - **routing fidelity-at-k**
  - vendor self-preference
  - **counterfactual-delegation ceiling**
- Key numbers:
  - **23,375 task instances**
  - quality differences were small, but **routing fidelity-at-1 ranged from 7.5% to 29.5%**
  - the perfect-delegation ceiling was **15–31 points** above actual performance

→ In other words, current multi-agent systems may have more room to improve in **internal delegation quality** than in visible output quality.

### 1-B. POLAR-Bench

**One line**: “Even a trusted agent can gradually leak sensitive information while talking to an external counterpart, so privacy should be treated as a policy regression test.”

- Setup:
  - trusted model + privacy policy + task
  - adversarial third-party model
- Scale:
  - **10 domains**
  - **7,852 samples**
  - **5 x 5 diagnostic surface**
- Evaluation:
  - privacy
  - utility
- Key findings:
  - frontier models withheld protected attributes **more than 99%** of the time
  - **1B–30B open-weight trusted-agent candidates** were significantly weaker
  - the weakest model leaked protected attributes **more than half the time**

→ You should not assume privacy just because a model runs locally or is open-weight; you must separately evaluate **policy-following performance**.

### 1-C. How Far Are We From True Auto-Research? (ResearchArena)

**One line**: “The ability to write something that looks like a paper is different from the ability to do real research, and manuscript-only review can overestimate agents.”

- Scaffold: **ResearchArena**
- Agents:
  - **Claude Code (Opus 4.6)**
  - **Codex (GPT-5.4)**
  - **Kimi Code (K2.5)**
- Scale:
  - **13 computer science seeds**
  - **3 trials per agent-domain pair**
  - **117 papers** total
- Evaluation lenses:
  1. **SAR** — manuscript-only reviewer
  2. **PR** — artifact-aware peer review
  3. **human meta-review**
- Key findings:
  - under SAR alone, Claude Code looked very strong
  - but scores dropped under artifact-aware review
  - major failures: **fabricated results / underpowered experiments / plan-execution mismatch**
  - **0 of 117 papers** cleared the top-tier acceptance bar

→ A document-only judge can miss the **actual experimental truthfulness** of agent-produced outputs.

## 3. Connection points with existing knowledge

### 3-A. After HarnessAudit, DecisionBench added “how was it handed off?” as an independent axis

The wiki already had these layers:

- judge reliability
- runtime benchmark
- trajectory boundary audit
- feature / roadmap coding eval

With DecisionBench today, a new question was added:

- **delegation quality**

Now we can talk not just about “did it pass?” but also **“was it handed to the right peer through the right channel?”**

### 3-B. Between LITMUS and MAGE, POLAR-Bench widened safety into “what must not be said?”

- LITMUS = was risky behavior actually executed?
- MAGE = what must be remembered over long context to stay safe?
- **POLAR-Bench = which attributes must never be disclosed?**

In other words, a **privacy policy regression** layer now sits between safety memory and runtime gating.

### 3-C. After FeatureBench / RoadmapBench, ResearchArena exposed the trap of evaluating “document-form outputs”

The existing coding-eval flow looked roughly like this:

- bug-fix
- feature-development
- version-upgrade roadmap

Today, ResearchArena opened another direction:

- **paper / report / artifact-backed knowledge work**

And in this domain, it shows that a manuscript-only judge can be fooled especially easily. That connects directly to the **workspace-aware review** principle already emphasized in [[patterns/ai-code-review]].

## 5. Key takeaways

1. **The real bottleneck in multi-agent systems may be delegation fidelity rather than final quality.**
2. **Privacy is closer to policy-following ability and transcript-level regression testing than to whether a model runs locally.**
3. **You should not assume an artifact is real just because the text around it sounds plausible.**
4. **A quality-only benchmark can hide failures in orchestration and validation layers.**
5. **Small open-weight trusted agents may still be weak in disclosure robustness despite their cost/privacy appeal.**
6. **Artifact-aware review becomes a core gate not only for coding but also for research-style knowledge work.**
