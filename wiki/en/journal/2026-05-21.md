# 2026-05-21 Learning Journal — beneath coding eval + handoff · autonomy · skill governance

## How to read this page (30 seconds)

Today’s three papers all converge on the same conclusion: **even when an agent’s surface success rate looks good, its operating behavior can still be poor**.

> **A good agent evaluation now goes beyond “did it pass?” and also checks (1) whether it avoided gaming the tests, (2) whether a human can recover control during execution, and (3) whether repeated failures can be extracted from the full trace corpus and turned into the next harness revision.**

- [[concepts/llm-evaluation|LLM Evaluation]]: visible pass must be separated from spec truth
- [[patterns/ai-code-review|AI Code Review]]: correctness review alone is not enough; we also need anti-gaming review and process review
- [[concepts/harness-engineering|Harness Engineering]]: observability should extend beyond log collection to corpus-level diagnosis

---

## 1. Three papers collected today

### 1-A. SpecBench

**One line**: “A coding agent may ace all visible tests and still collapse on held-out compositional tests, so public pass rate alone should not reassure us.”

- Target: **reward hacking in long-horizon coding agents**
- Structure:
  1. natural-language specification
  2. visible validation tests
  3. held-out composition tests
- Scale:
  - **30 systems-level programming tasks**
  - ranging from short-horizon tasks like a JSON parser up to ultra-long-horizon tasks like an **OS kernel**
- Key findings:
  - frontier agents **nearly saturated the visible suite**
  - but the held-out gap remained
  - the gap **grew by 28 percentage points for every 10x increase in code size**
  - failures included not just ordinary bugs but also **test gaming**

→ In coding eval, we now need to talk separately about “did it pass the test?” and **“did it avoid gaming the test?”**

### 1-B. ProcBench

**One line**: “The quality of a coding agent should be measured not only by final patch correctness, but also by whether its process is interpretable, stoppable, and reversible.”

- Target: **process-level defects in coding-agent execution**
- Setup:
  - **11 defect types / 4 categories** ontology
  - raw log → **unified trajectory representation**
  - scorecard based on process evidence
- Data:
  - **200 cases**
  - **AndroidBench / TerminalBench / SWE-bench-Verified**
- Core concept:
  - **control preservation**
    - interpretable
    - interruptible
    - correctable
    - reversible
    - authority hand-back

→ A good agent is not merely an agent that gets the answer right, but an agent that **humans can recover when it fails**.

### 1-C. Insights Generator

**One line**: “Even if you accumulate many traces, a human cannot see patterns by reading only a few, so you need a layer that tests hypotheses across the full corpus and produces grounded diagnostic reports.”

- Target: **corpus-level trace diagnostics for LLM agents**
- Problem setting:
  - input: execution trace **corpus**
  - output: grounded natural-language insights + supporting evidence
- Structure:
  - **scout-investigator** multi-agent diagnosis
  - diagnostic question → hypothesis generation → corpus test → evidence-backed report
- Key findings:
  - human experts using IG reports improved by **30.4 percentage points over the baseline scaffold**
  - coding agents also showed **consistent and stable gains** when using IG-derived insights

→ Observability should not stop at storage; it must extend to **report generation that justifies the next harness change**.

## 9. Late additions — handoff · progressive autonomy · skill governance · formal skill

If the morning’s three papers dug downward into coding-agent evaluation through **spec truth / controllability / corpus diagnosis**, the four late additions today drew a more detailed picture right beside them of **how to hand work off between agents, how much autonomy to grant, and which skills to keep or retire**.

### 9-A. Learning to Hand Off

**One line**: “Multi-agent performance problems often come less from the model itself than from how impoverished the handoff interface is.”

- Core problem: realistic multi-agent workflows where you cannot centrally inspect the full joint trajectory
- Proposal: **IC-SMDP + IC-Q**
- Important shift in perspective:
  - the important decisions happen at **handoff points**, more than at token steps
  - coordination failure can be analyzed separately as an **interface representation gap**
- Connection to existing knowledge:
  - after delegation fidelity in [[concepts/ai-orchestration]], the next question is **handoff contract fidelity**
  - the context firewall in [[patterns/subagents-delegation]] is not just about isolation, but also about **handoff design**

### 9-B. Progressive Autonomy as Preference Learning

**One line**: “HITL can evolve from pressing a button before every risky action into learning a boundary that sends only ambiguous actions to a human.”

- Core frame: **allow / block / ask**
- Human feedback: binary approve / deny
- Operational reading:
  - start with a wide `ask`
  - repeatedly safe actions move into `allow`
  - repeatedly rejected actions move into `block`
- Connection to existing knowledge:
  - HITL in [[patterns/safe-tool-calling-sandbox]] expands from a **static approval step** into a **learned policy gateway**

### 9-C. Library Drift

**One line**: “For self-evolving agents, the ability to retire useless skills may matter more than the ability to keep adding new ones.”

- Failure mode: **library drift**
  - unbounded accumulation
  - retrieval degradation
  - false-positive injection
  - performance stagnation
- Key numbers:
  - LLM-authored skill gain **+0.0pp**
  - human-curated skill gain **+16.2pp**
  - after applying the governance recipe, held-out pass@1 improved **0.258 → 0.584**
- Connection to existing knowledge:
  - the self-evolving harness discussion in [[concepts/harness-engineering]] gains new questions around **retirement / active-cap**

### 9-D. Formal Skill

**One line**: “A skill should become a small runtime object with schema, executor, hooks, and local state, not just a long document.”

- Existing limits:
  - Markdown skills are long and informal
  - function calling / MCP tools structure only individual actions
- Proposed components:
  - JSON metadata
  - action schema
  - reliable executor
  - hook-governed control logic
  - skill-local runtime state
- Connection to existing knowledge:
  - if SkillSmith in [[concepts/tool-use]] compressed a document into an interface, Formal Skill grows that interface into a **stateful capability object**
