# 2026-05-20 학습 일지 — delegation substrate · privacy diagnostic · artifact-aware auto-research

## 이 글을 읽는 법 (30초)

오늘 3편은 모두 **겉보기 성공률 하나만으로는 agent를 이해할 수 없다**는 같은 결론으로 모인다.

> **좋은 에이전트 평가는 "결과가 괜찮았나"만 묻지 않고, (1) 누구에게 왜 넘겼는지, (2) 무엇을 말하면 안 됐는지, (3) 문서 뒤에 실제 artifact가 있는지까지 함께 본다.**

- [[concepts/ai-orchestration|AI 오케스트레이션]]: delegation은 quality-only score로는 거의 안 보일 수 있다
- [[concepts/agent-supply-chain-security|Agent Supply Chain Security]]: privacy는 도구 권한만이 아니라 **대화 중 속성 누설** 문제다
- [[concepts/llm-evaluation|LLM Evaluation]]: manuscript-only review는 plausibility를 과대평가할 수 있다

---

## 1. 오늘 수집한 3편

### 1-A. DecisionBench

**한 줄**: "멀티에이전트가 잘 위임했는지는 최종 정답률보다 routing fidelity를 봐야 드러난다."

- 대상: **emergent delegation in long-horizon workflows**
- 구성:
  - **GAIA / tau-bench / BFCL multi-turn**
  - **11 models / 7 vendor families**
  - `call_model` + optional `read_profile`
- metric:
  - quality
  - cost
  - latency
  - delegation rate
  - **routing fidelity-at-k**
  - vendor self-preference
  - **counterfactual-delegation ceiling**
- 핵심 수치:
  - **23,375 task instances**
  - quality 차이는 작지만 **routing fidelity-at-1은 7.5% ~ 29.5%**
  - perfect delegation ceiling은 실제보다 **15~31 points** 높음

→ 즉 지금 멀티에이전트 시스템은 "보이는 품질"보다 **내부 위임 품질**에서 더 큰 개선 여지가 남아 있다.

### 1-B. POLAR-Bench

**한 줄**: "trusted agent도 외부 상대와 대화하다 보면 민감 정보를 조금씩 흘릴 수 있으므로, privacy는 정책 회귀 테스트로 다뤄야 한다."

- 설정:
  - trusted model + privacy policy + task
  - adversarial third-party model
- 규모:
  - **10 domains**
  - **7,852 samples**
  - **5 x 5 diagnostic surface**
- 평가:
  - privacy
  - utility
- 핵심 발견:
  - frontier model은 protected attribute를 **99% 이상 withholding**
  - **1B~30B open-weight trusted-agent 후보**는 현저히 약함
  - weakest model은 protected attribute를 **절반 이상 유출**

→ 로컬 실행이나 오픈웨이트라는 이유만으로 privacy를 가정하면 안 되고, **policy-following 성능**을 따로 봐야 한다.

### 1-C. How Far Are We From True Auto-Research? (ResearchArena)

**한 줄**: "논문처럼 보이게 쓰는 능력과 진짜 연구를 수행하는 능력은 다르며, manuscript-only review는 agent를 과대평가할 수 있다."

- scaffold: **ResearchArena**
- agent:
  - **Claude Code (Opus 4.6)**
  - **Codex (GPT-5.4)**
  - **Kimi Code (K2.5)**
- 규모:
  - **13 computer science seeds**
  - **3 trials per agent-domain pair**
  - 총 **117 papers**
- 평가 렌즈:
  1. **SAR** — manuscript-only reviewer
  2. **PR** — artifact-aware peer review
  3. **human meta-review**
- 핵심 발견:
  - SAR만 보면 Claude Code는 매우 강해 보임
  - 하지만 artifact-aware review에서는 점수가 하락
  - 주요 실패: **fabricated results / underpowered experiments / plan-execution mismatch**
  - **117편 중 top-tier acceptance bar 통과 0편**

→ 문서 judge만으로는 에이전트가 만든 산출물의 **실제 실험적 진실성**을 놓칠 수 있다.

## 2. 오늘의 연결 그림

| 층 | 오늘 소스 | 새로 선명해진 질문 |
|---|---|---|
| **위임 구조** | DecisionBench | 누구에게 왜 넘겼는지를 최종 정답률과 분리해 측정하는가? |
| **정보 경계** | POLAR-Bench | agent가 해야 할 말과 하면 안 될 말을 동시에 관리하는가? |
| **산출물 검증** | ResearchArena | 그럴듯한 문서 뒤에 실제 artifact와 실행 진실이 있는가? |

세 편을 한 줄로 압축하면 이렇다.

1. **오케스트레이션은 품질만으로 평가하면 잘못된 결론이 나올 수 있다.**
2. **보안은 실행 권한 통제뿐 아니라 대화 중 속성 누설 통제까지 포함한다.**
3. **평가는 텍스트 plausibility를 넘어 artifact truth를 봐야 한다.**

## 3. 기존 지식과의 연결 포인트

### 3-A. HarnessAudit 다음에 DecisionBench가 붙으면서 "어떻게 넘겼는가"가 독립 축이 됐다

최근 위키는 이미 다음 층을 갖고 있었다.

- judge reliability
- runtime benchmark
- trajectory boundary audit
- feature / roadmap coding eval

오늘 DecisionBench가 들어오면서 여기에

- **delegation quality**

라는 새 질문이 붙었다. 이제는 "통과했는가"뿐 아니라 **"적절한 peer에게 적절한 채널로 넘겼는가"** 를 따로 말할 수 있다.

### 3-B. LITMUS와 MAGE 사이에 POLAR-Bench가 들어오며 safety가 "무엇을 말하지 말아야 하나"까지 넓어졌다

- LITMUS = 위험 행동이 실제 실행됐는가
- MAGE = 장시간 맥락에서 무엇을 잊지 말아야 안전한가
- **POLAR-Bench = 어떤 속성은 끝까지 말하지 않아야 하는가**

즉 safety memory와 runtime gating 사이에 **privacy policy regression** 층이 생긴 셈이다.

### 3-C. FeatureBench / RoadmapBench 다음에 ResearchArena가 들어오며 "문서형 산출물" 평가의 함정이 드러났다

기존 coding eval 흐름은 대략 이랬다.

- bug-fix
- feature-development
- version-upgrade roadmap

오늘 ResearchArena는 다른 방향을 연다.

- **paper / report / artifact-backed knowledge work**

그리고 이 도메인에서는 manuscript-only judge가 특히 쉽게 속을 수 있음을 보여 준다. 이건 [[patterns/ai-code-review]] 에서 이미 강조하던 **workspace-aware review** 원칙과도 맞닿는다.

## 5. 핵심 배움

1. **멀티에이전트의 진짜 병목은 최종 품질보다 delegation fidelity일 수 있다.**
2. **privacy는 로컬 실행 여부보다 policy-following 능력과 transcript-level regression test에 더 가깝다.**
3. **텍스트가 그럴듯하다는 이유로 artifact가 진짜라고 가정하면 안 된다.**
4. **quality-only benchmark는 오케스트레이션과 검증 레이어의 실패를 가릴 수 있다.**
5. **작은 open-weight trusted agent는 cost/privacy 매력과 별개로 disclosure robustness가 취약할 수 있다.**
6. **artifact-aware review는 코딩뿐 아니라 연구형 knowledge work에서도 핵심 gate가 된다.**
