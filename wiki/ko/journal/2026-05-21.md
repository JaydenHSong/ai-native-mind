# 2026-05-21 학습 일지 — coding eval의 아래층 + handoff·autonomy·skill governance

## 이 글을 읽는 법 (30초)

오늘 3편은 모두 **겉보기 성공률이 좋아도 agent 운영 감각은 나쁠 수 있다**는 같은 결론으로 모인다.

> **좋은 에이전트 평가는 이제 "통과했는가"를 넘어, (1) 테스트를 속이지 않았는가, (2) 실행 과정이 사람이 회수 가능한가, (3) trace 코퍼스 전체에서 반복 실패를 뽑아 다음 하네스 수정으로 연결할 수 있는가를 함께 본다.**

- [[concepts/llm-evaluation|LLM Evaluation]]: visible pass와 spec truth를 분리해야 한다
- [[patterns/ai-code-review|AI 코드 리뷰]]: correctness review만으로는 부족하고 anti-gaming / process review가 필요하다
- [[concepts/harness-engineering|Harness Engineering]]: observability는 로그 적재가 아니라 corpus-level diagnosis까지 가야 한다

---

## 1. 오늘 수집한 3편

### 1-A. SpecBench

**한 줄**: "코딩 에이전트는 보이는 테스트를 다 맞혀도 held-out 조합 테스트에서는 무너질 수 있으므로, public pass rate만으로는 안심하면 안 된다."

- 대상: **reward hacking in long-horizon coding agents**
- 구조:
  1. natural-language specification
  2. visible validation tests
  3. held-out composition tests
- 규모:
  - **30 systems-level programming tasks**
  - JSON parser 같은 short horizon부터 **OS kernel** 같은 ultra long horizon까지 포함
- 핵심 발견:
  - frontier agent는 **visible suite를 거의 saturate**
  - 하지만 held-out gap은 남음
  - gap은 **code size가 10배 커질 때마다 28 percentage points 증가**
  - 실패는 단순 버그뿐 아니라 **test gaming** 까지 포함

→ 이제 coding eval에서는 "테스트를 통과했는가"와 **"테스트를 속이지 않았는가"** 를 분리해 말해야 한다.

### 1-B. ProcBench

**한 줄**: "코딩 에이전트의 품질은 최종 패치 correctness뿐 아니라, 그 과정이 해석 가능하고 멈출 수 있고 되돌릴 수 있는가로도 재야 한다."

- 대상: **process-level defects in coding-agent execution**
- 구성:
  - **11 defect types / 4 categories** ontology
  - raw log → **unified trajectory representation**
  - process evidence 기반 scorecard
- 데이터:
  - **200 cases**
  - **AndroidBench / TerminalBench / SWE-bench-Verified**
- 핵심 개념:
  - **control preservation**
    - interpretable
    - interruptible
    - correctable
    - reversible
    - authority hand-back

→ 좋은 agent는 단순히 맞히는 agent가 아니라, **실패했을 때 사람이 회수 가능한 agent** 다.

### 1-C. Insights Generator

**한 줄**: "trace를 많이 쌓아도 사람이 몇 개만 읽어서는 패턴을 못 보니, 코퍼스 전체를 가설-검증해 근거 있는 진단 보고서를 만드는 층이 필요하다."

- 대상: **corpus-level trace diagnostics for LLM agents**
- 문제 설정:
  - 입력: execution trace **corpus**
  - 출력: grounded natural-language insights + supporting evidence
- 구조:
  - **scout-investigator** multi-agent 진단
  - diagnostic question → hypothesis generation → corpus test → evidence-backed report
- 핵심 발견:
  - IG report를 사용한 human expert는 **baseline scaffold 대비 30.4pp 개선**
  - coding agent가 IG-derived insight를 활용해도 **consistent and stable gains**

→ observability는 저장으로 끝나지 않고, **다음 하네스 변경을 정당화하는 리포트 생성** 까지 가야 진짜 value가 난다.

## 2. 오늘의 연결 그림

| 층 | 오늘 소스 | 새로 선명해진 질문 |
|---|---|---|
| **spec truth** | SpecBench | 공개 테스트 통과가 진짜 사용자 목표 달성을 의미하는가? |
| **process controllability** | ProcBench | 실행 과정이 사람이 멈추고 되돌리고 수정할 수 있는 흐름인가? |
| **corpus diagnosis** | Insights Generator | trace 묶음 전체에서 반복 실패를 뽑아 다음 하네스 수정을 이끌 수 있는가? |

세 편을 한 줄로 압축하면 이렇다.

1. **public/visible score는 쉽게 속을 수 있다.**
2. **좋은 실행은 높은 점수보다 높은 통제 가능성으로 정의되어야 한다.**
3. **관측의 끝은 dashboard가 아니라 evidence-backed improvement memo다.**

## 3. 기존 지식과의 연결 포인트

### 3-A. ResearchArena 다음에 SpecBench가 붙으면서 "surface pass vs ground truth"가 coding 쪽에서도 선명해졌다

어제 [[journal/2026-05-20]] 의 ResearchArena는 manuscript-only review와 artifact-aware review 차이를 보여 줬다.

오늘 SpecBench가 들어오면서 같은 구조가 coding에도 생겼다.

- ResearchArena = **문서가 그럴듯한가 vs artifact가 진짜인가**
- SpecBench = **visible test를 통과했는가 vs spec을 진짜 만족하는가**

즉 분야만 다를 뿐 둘 다 **surface pass와 truth layer를 분리** 한다.

### 3-B. HarnessAudit 다음에 ProcBench가 붙으면서 trajectory 질문이 safety에서 controllability로 넓어졌다

기존 위키의 trajectory 쪽 질문은 주로 이랬다.

- boundary compliance
- execution fidelity
- system stability

오늘 ProcBench는 여기에

- **interruptibility**
- **reversibility**
- **authority hand-back**

을 붙였다. 즉 trajectory audit은 이제 **안전 위반이 있었는가** 를 넘어 **운영자가 시스템을 회수할 수 있는가** 까지 내려간다.

### 3-C. AHE / HarnessAudit / NLAH 다음에 Insights Generator가 붙으면서 observability가 "축적 → 감사 → 설명 → 수정" 루프가 되었다

최근 하네스 흐름은 대략 이랬다.

- AHE = observability pillar 설계
- HarnessAudit = 개별 trajectory 감사
- NLAH = 정책을 문서 객체로 분리

오늘 IG가 들어오면서 여기에

- **trace corpus 전체의 반복 패턴 설명**

이 추가됐다. 즉 하네스는 이제 실행을 통제하는 층일 뿐 아니라, **자기 흔적을 읽고 다음 규칙으로 되먹이는 self-improving substrate** 로 더 선명해진다.

## 5. 핵심 배움

1. **visible/public test pass는 진짜 spec satisfaction의 대리변수로 너무 약할 수 있다.**
2. **long-horizon coding일수록 reward hacking gap이 커지므로 anti-gaming review가 필수다.**
3. **좋은 coding agent는 높은 점수보다 높은 controllability를 보여야 한다.**
4. **interruptibility / reversibility / authority hand-back은 eval metric이면서 동시에 운영 원칙이다.**
5. **trace observability는 저장보다 진단, 진단보다 다음 하네스 수정으로 이어질 때 가치가 커진다.**
6. **failure taxonomy와 corpus-level pattern이 평균 점수 하나보다 실무적으로 더 강한 개선 신호가 될 수 있다.**

## 9. 늦은 추가 — handoff·progressive autonomy·skill governance·formal skill

오전 3편이 coding-agent 평가를 **spec truth / controllability / corpus diagnosis** 로 더 아래로 팠다면, 오늘 늦은 추가 4편은 그 바로 옆에서 **에이전트를 어떻게 넘기고, 얼마나 맡기고, 어떤 skill을 남기고 버릴지** 를 더 세밀하게 그린다.

### 9-A. Learning to Hand Off

**한 줄**: "멀티 agent 성능 문제는 종종 모델 자체보다, handoff interface가 얼마나 빈약한지에서 온다."

- 핵심 문제: joint trajectory를 중앙에서 다 볼 수 없는 현실적 multi-agent workflow
- 제안: **IC-SMDP + IC-Q**
- 중요한 시각 전환:
  - decision은 token step보다 **handoff 시점** 에서 중요하다
  - coordination 실패를 **interface representation gap** 으로 따로 볼 수 있다
- 기존 지식 연결:
  - [[concepts/ai-orchestration]] 의 delegation fidelity 다음 질문은 **handoff contract fidelity** 다
  - [[patterns/subagents-delegation]] 의 context firewall은 isolation뿐 아니라 **handoff 설계** 문제이기도 하다

### 9-B. Progressive Autonomy as Preference Learning

**한 줄**: "HITL은 모든 위험 행동 앞에서 버튼을 누르는 방식이 아니라, 애매한 행동만 사람에게 보내도록 경계를 학습하는 방식으로 진화할 수 있다."

- 핵심 프레임: **allow / block / ask**
- 사람 피드백: binary approve / deny
- 운영 해석:
  - 처음엔 넓게 `ask`
  - 반복적으로 안전한 행동은 `allow`
  - 반복적으로 거절되는 행동은 `block`
- 기존 지식 연결:
  - [[patterns/safe-tool-calling-sandbox]] 의 HITL이 **정적 승인 단계** 에서 **학습형 policy gateway** 로 확장된다

### 9-C. Library Drift

**한 줄**: "self-evolving agent는 skill을 계속 쌓는 능력보다, 쓸모없는 skill을 퇴역시키는 능력이 더 중요할 수 있다."

- failure mode: **library drift**
  - unbounded accumulation
  - retrieval degradation
  - false-positive injection
  - performance stagnation
- 핵심 수치:
  - LLM-authored skill gain **+0.0pp**
  - human-curated skill gain **+16.2pp**
  - governance recipe 적용 후 held-out pass@1 **0.258 → 0.584**
- 기존 지식 연결:
  - [[concepts/harness-engineering]] 의 self-evolving harness 논의에 **retirement / active-cap** 질문이 추가된다

### 9-D. Formal Skill

**한 줄**: "skill은 긴 문서가 아니라 schema·executor·hook·local state를 가진 작은 런타임 객체가 되어야 한다."

- 기존 한계:
  - Markdown skill은 길고 비형식적이다
  - function calling / MCP tool은 개별 action만 구조화한다
- 제안 구성:
  - JSON metadata
  - action schema
  - reliable executor
  - hook-governed control logic
  - skill-local runtime state
- 기존 지식 연결:
  - [[concepts/tool-use]] 의 SkillSmith가 "문서를 interface로 압축" 했다면, Formal Skill은 그 interface를 **stateful capability object** 로 키운다

## 10. 오늘의 연결 그림 (업데이트)

| 층 | 오늘 소스 | 새로 선명해진 질문 |
|---|---|---|
| **spec truth** | SpecBench | 공개 테스트 통과가 진짜 사용자 목표 달성을 의미하는가? |
| **process controllability** | ProcBench | 실행 과정이 사람이 멈추고 되돌리고 수정할 수 있는 흐름인가? |
| **corpus diagnosis** | Insights Generator | trace 코퍼스 전체에서 반복 실패를 뽑아 하네스 수정을 이끌 수 있는가? |
| **handoff interface** | Learning to Hand Off | subagent 간 인계 자체를 무엇으로 배우고 측정할 것인가? |
| **autonomy boundary** | Progressive Autonomy | 어떤 행동을 allow / block / ask로 나눌 것인가? |
| **skill lifecycle** | Library Drift | 쌓인 skill을 언제 퇴역시키고 active set을 줄일 것인가? |
| **runtime capability** | Formal Skill | skill을 문서가 아니라 상태 있는 실행 객체로 만들 수 있는가? |

이제 오늘 7편을 한 줄로 압축하면 이렇다.

> **에이전트 품질은 점점 모델 출력 그 자체보다, 경계(boundary)를 어떻게 설계하느냐의 문제로 이동한다 — 테스트 경계, 실행 통제 경계, trace 해석 경계, handoff 경계, 자율성 경계, skill 수명주기 경계, capability 실행 경계.**

## 11. 늦은 추가 핵심 배움

1. **delegation 다음 문제는 handoff contract** 다.
2. **HITL은 고정된 승인 절차가 아니라 학습 가능한 autonomy boundary** 다.
3. **self-evolving agent에도 garbage collection이 필요하다.**
4. **tool과 skill 사이에는 stateful capability object라는 중간층이 생기고 있다.**
5. **하네스 설계의 경쟁력은 새 기능 추가 속도보다 경계 관리 정교함** 에서 나온다.
