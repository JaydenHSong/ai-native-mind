# 2026-05-01 학습 일지 — 에이전트 스택의 stratification + 금요 회고

## 이 글을 읽는 법 (30초)

오늘은 두 가지를 동시에 한다.

1. **데일리 인제스트**: AI 에이전트 엔지니어링 기사 3편을 raw에 정리하고, 위키의 `harness-engineering` · `gen-ai-observability` · `agentic-engineering` 페이지에 연결한다.
2. **금요 회고**: 위키 안에서 겹치는 영역을 점검한다 — 기존 링크와 핵심 내용은 절대 건드리지 않고, 어디가 두 페이지로 나뉘어 있는지·어디서 한 번 더 묶을 수 있는지만 기록한다.

## 오늘 배운 것 (3개 소스)

- **["The Agent Stack in 2026: Layers, Harnesses, and Where You Actually Build" — Hieu TRAN, dev.to (2026-04-14)](https://dev.to/hieu_tran_80c388add84c060/the-agent-stack-in-2026-layers-harnesses-and-where-you-actually-build-2e5g)** — Anthropic Managed Agents (4월 8일 public beta)와 LangChain Deep Agents Deploy 출시를 계기로 에이전트 스택이 "직접 짜기 ↔ 설정만 하기"의 4 레이어 스펙트럼으로 stratify되었음. 핵심 메시지 두 가지: (1) **에이전트 정체성·능력은 이식 가능한 정의 레이어로, 실행·메모리·보안·배포는 그 아래 인프라로** 분리하라. (2) Anthropic의 [Harness Design 글](https://www.anthropic.com/engineering/harness-design-long-running-apps)이 보여주듯 모델이 좋아지면 **하네스를 줄이는 게 자연스러운 응답**이다. 보너스로 ClawHavoc(2026-02 OpenClaw ClawHub 공급망 공격, 1,184개 악성 스킬·Snyk ToxicSkills 보고서 36.8% 취약) 사례가 "컨텍스트 레벨 정의는 자격증명 격리 없이는 못 산다"는 것을 보여줌.

- **["AI Agent Observability — Evolving Standards and Best Practices" — Guangya Liu (IBM) & Sujay Solomon (Google), OpenTelemetry Blog (2025-03-06)](https://opentelemetry.io/blog/2025/ai-agent-observability/)** — 에이전트는 비결정적이라 텔레메트리가 **장애 대응을 넘어 품질 평가의 피드백 루프 입력**으로 쓰인다. 이를 위해선 벤더 중립 시맨틱 컨벤션이 필수. OTel은 (1) Agent application semconv, (2) Agent framework semconv (LangGraph·CrewAI·AutoGen·IBM Bee 등 공통), (3) GenAI semconv 세 층을 표준화 중. 계측은 **baked-in (CrewAI 식)** vs **외부 OTel 패키지 (Traceloop/Langtrace, 또는 OTel-owned `instrumentation-genai`)** 두 갈래 — 트레이드오프 표가 실무 의사결정에 바로 쓰인다. **AI agent application ≠ AI agent framework** 구분이 명료해서 위키 `gen-ai-observability` 본문에 그대로 들여올 가치가 있음.

- **["Agentic Engineering: How Swarms of AI Agents Are Redefining Software Engineering" — Renuka Kumar & Prashanth Ramagopal (Cisco), LangChain Blog (2026-04-17)](https://www.langchain.com/blog/agentic-engineering-redefining-software-engineering)** — 코딩 AI를 더 빠르게가 아니라, 실제 엔지니어링 팀처럼 동작하는 **multi-agent 제어 평면**. **Worker Agent**(개별 기여자, 의도 해석→계획→컨텍스트 수집→실행→검증→보고)와 **Leader Agent**(공유 프롬프트·툴 게이트웨이·장기 메모리·글로벌 관측·오케스트레이션) 두 역할. LangGraph + LangSmith + LangMem로 구현. 파일럿 수치(보수적): 디버깅 워크플로 **time-to-root-cause 93% 단축**, 한 달 70명 512세션에서 200+ man-hour 절감, 개발 워크플로 **65% 실행 시간 단축** — 단 가장 큰 이득은 코드 생성 가속이 아니라 **PR merge 이후 downstream 테스팅 압축**에서 왔고, **새 병목은 PR 리뷰(HITL 게이트) 자체**.

## 인사이트

세 글이 한 그림으로 모인다.

- **Hieu TRAN의 스택 글**은 "어디 레이어에 살 것인가"를 묻고
- **OTel 블로그**는 "어느 레이어든 텔레메트리는 표준에 맞춰라"를 말하고
- **Cisco 파일럿**은 "Worker/Leader 같은 제어 평면을 LangGraph 위에 얹어보니 코드 생성이 아니라 조정 비용이 압축되더라"를 보여준다.

세 메시지는 [[concepts/harness-engineering]]·[[concepts/agentic-engineering]] 페이지의 기존 라인 — "사람은 on the loop, 하네스는 표준 텔레메트리를 가진다" — 와 충돌하지 않고 그 위에 더 진해진 색을 칠한다. 다음 액션은 **모델 업그레이드(예: Claude 4.6 → 다음)** 가 있을 때 실제로 우리 `examples/` 하네스에서 무엇을 **줄일 수 있는지** 한 번 점검해 보는 것.

## 금요 회고 — 위키 중복·압축 후보 (2026-05-01)

원칙: **링크와 핵심 내용은 보존**. 본 회고는 "이렇게 묶었다"가 아니라 "어디가 묶일 만한지"의 메모. 실제 머지는 사용자 확인이 있을 때 한다.

### 명확하게 분리되어 있고 그대로 두는 것이 좋은 페어

- [[concepts/harness-engineering]] (개념) ↔ [[patterns/harness-engineering-casebook]] (도메인 30케이스 매트릭스): **개념 vs 케이스북** 구분이 분명. 합치지 말 것.
- [[concepts/ai-orchestration]] (개념) ↔ [[patterns/orchestration-patterns-practice]] (커리큘럼 5 실습): **이론 vs 실습**. 합치지 말 것.
- [[concepts/context-engineering]] ↔ [[concepts/context-vs-prompt-practice]]: 후자는 커리큘럼 1편이라 의도적으로 별도. 합치지 말 것.

### 실제로 살짝 겹치는 영역 — 압축이 아니라 "교차 링크 보강"이 답

- [[patterns/agent-server-harness]] ↔ [[patterns/harness-building-blocks]]: 둘 다 하네스 구성 요소를 다루지만, 전자는 **HTTP·큐·SSE 뒤의 서버 하네스**, 후자는 **Guides/Sensors 일반 빌딩 블록**. 그러나 내용에 약 15% 겹침이 있음. **다음 인제스트 때** "어느 페이지에 무엇을 적을지" 가이드를 양쪽 페이지 상단에 한 줄씩 넣자(다음 주 작업 후보, 사용자 승인 시).
- [[patterns/agent-planning-to-implementation]] ↔ [[patterns/agent-server-harness]] ↔ [[patterns/harness-engineering-casebook]]: 셋이 같은 "기획→코드" 파이프라인을 다른 각도(파이프라인 / 서버 / 케이스북)에서 본다. 케이스북에 이미 매핑이 있어 OK.
- [[concepts/agentic-engineering]] ↔ [[patterns/vibe-coding-antipatterns]]: 한쪽은 "agentic이 vibe의 성숙형"이라고 정의, 다른 한쪽은 "vibe의 안티패턴". 같은 축의 양 끝이라 교차 링크가 충분하면 OK — 두 페이지 모두 이미 서로 링크하고 있음. 추가 작업 불필요.
