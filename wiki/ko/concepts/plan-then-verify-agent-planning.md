# Plan-Then-Verify — 실행 전에 검증부터 하는 에이전트 계획 패턴

## 쉽게 읽기

**비유**: 시공 전에 설계도를 구조 검토받고, 고칠 수 있는 것만 한 번 고치고, 안 되면 "못 짓겠다"고 말하는 셈이다. 실행 중 사고를 사후 수습하지 않고 계획 단계에서 차단한다.

| 용어 | 풀이 |
|------|------|
| **태스크 그래프** | 작업을 단계·의존성·산출물로 구조화한 그래프 |
| **결정적 검증기** | LLM이 아니라 규칙으로 함수·산출물·순서 제약을 검사하는 모듈 |
| **안전 기권** | 지원 불가 요청에 능력을 지어내지 않고 실행을 거부하는 것 |

## 한줄 정의

2026-11-01 MDPI 게재 — 플래너가 만든 구조화 계획을 결정적 검증기가 문서화된 지식베이스에 비춰 실행 전에 검사하고, 1회 제한 수리만 허용하며, 지원 불가 시 안전하게 기권하는 에이전트 계획 패턴.

## 핵심 내용

- **파이프라인**: 플래너 → 결정적 검증기(함수·아티팩트·순서 제약 검사) → 1회 제한 수리 패스 → 검증기 이슈 집합이 비면 실행, 남으면 안전 기권.
- **벤치마크 Core-60**: 지원·다단계·수리 민감·지원 불가 요청을 아우르는 60개 태스크 공개 벤치마크. 벤치마크·지식베이스 스냅샷·구현·분석 자료·논문 소스가 GitLab에 공개됐다.
- **결과**: Gemma·Devstral·DeepSeek 등 여러 모델군에서 Plan-and-Execute 대비 정적 적합성 점수가 크게 개선됐고, 토큰 비용은 Plan-and-Execute 수준에 근접했다. GPT-OSS·GLM은 테스트 서빙 스택에서 구조화 출력이 무너져 효과가 거의 없었다.
- **설계 포인트**: 검증의 근거는 문서화된 운영 지식베이스다. 검증기가 '아는 것' 밖의 계획은 통과하지 못하므로, 지식베이스의 품질이 곧 패턴의 천장이다.

## 왜 중요한가 (1인 개발자 관점)

1. **실행 전 게이트는 1인 개발자의 안전망이다**: 에이전트가 도구·결제·외부 시스템에 닿기 전에 계획을 검증하면, 사후 롤백보다 싼 비용으로 사고를 막는다.
2. **기권도 기능이다**: 지원 불가 요청에 그럴듯한 계획을 지어내는 것보다 "못 한다"고 말하는 편이 신뢰를 지킨다. PTV는 기권을 설계 요소로 넣었다.
3. **검증기는 LLM이 아니어도 된다**: 규칙 기반 검증은 재현 가능하고 비용이 싸다. 하네스 설계에서 '계획-검증 분리'는 바로 적용 가능한 패턴이다.

## 한계 (명시)

- 주 벤치마크는 정적이며 실제 도구를 호출하지 않는다. 보조 샌드박스 리플레이만 저장된 계획을 모의 도구로 실행했다.
- 보고된 점수는 실제 실행 성공률이 아니라 지원 성공 + 올바른 기권을 합친 적합성 점수다.
- 단일 논문 출처이며 독립 재현·2차 보도가 아직 없다.
