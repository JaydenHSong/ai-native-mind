# Anthropic의 에이전트 메모리 "dreaming" — 세션 사이 오프라인 정리로 틀린 메모를 고치고 위키를 쌓는다

## 쉽게 읽기

**비유**: 사람이 자면서 낮의 기억을 정리하듯, Claude도 세션이 끝난 뒤 "자는 시간"에 자기 일지를 다시 읽는다. 틀린 메모를 고치고, 흩어진 메모를 위키로 엮고, 다음 날 아침 책상 위에 올려둘 메모만 골라둔다. 잠자는 동안 공부하는 셈이다 — 단, 잠자는 시간에도 전기는 든다.

| 용어 | 풀이 |
|------|------|
| **Dreaming** | 세션 사이 오프라인 시간에 로그를 되돌아보며 메모를 고치고 지식을 정리하는 과정 |
| **Sleep-time compute** | 모델이 상호작용하지 않는 유휴 시간에 기존 맥락을 재구성하는 연구 아이디어 (Letta·UC Berkeley) |
| **CL-Bench** | Continual Learning Bench — 계속 배우는 능력을 재는 벤치마크 |

## 한줄 정의

2026-11-06 Anthropic 엔지니어링 블로그 "The components of agent memory"(Lance Martin) — Claude의 세션 간 메모리가 어떻게 동작하는지 공개했다. 핵심은 "dreaming"이다. 세션 사이 오프라인 시간에 Claude가 자기 로그를 다시 읽어 틀린 메모를 고치고, 새 메모를 쓰고, 연결된 위키 페이지를 만들고, 다음 세션에 무엇을 올릴지 정한다. 인간의 수면 중 기억 통합에서 따온 아이디어로, Letta와 UC Berkeley의 sleep-time compute 연구를 인용했다.

## 핵심 내용

- **정의**: Anthropic은 에이전트 메모리를 "경험에서 얻은 지식을 세션 사이에 파일로 남겨 나중에 읽을 수 있는 맥락"으로 좁게 정의한다. 가중치 변경, 한 대화 안의 인컨텍스트 학습, 오래된 대화를 요약으로 대체하는 compaction은 메모리에서 제외한다.
- **4개 층**: (1) 전사(transcripts) — 대화·활동 로그를 그대로 보존, (2) 메모리 노트 — Claude가 고른 교훈·규칙·목표·계획, (3) 메모리 표현 — 위키 같은 연결된 지식 구조, (4) 주입 맥락 — 매 세션 시작 시 미리 올리는 작은 메모리 층. dreaming은 이 층들 사이에서 동작한다.
- **설계 규칙**: "메모리가 무엇을 위한 것인지는 알려주되, 어떻게 쓸지는 알려주지 말라"는 것이 핵심 규칙이다. 강한 모델에게 실패만 기록하라고 지시하면 오히려 약해졌다. Claude Code의 자동 메모리는 MEMORY.md의 첫 200줄 또는 25KB까지만 인덱스로 올린다. 항상 올리는 층은 작게 유지해야 한다.
- **실험 결과**: CL-Bench 1.0 데이터베이스 과제에서 메모리 보유 시 Opus 5.5는 0.655→0.838, Sonnet 5.5는 0.644→0.833, Opus 5는 0.564→0.828로 올랐다. 포켓몬스터 레드에서는 Sonnet 3.7이 225개 폴더에 413개 파일(약 978,000자)을 남기고 배지 1개, Fable 5는 파일 9개+대시보드 1개(약 43,400자)로 배지 4개를 얻었다. Mt. Moon 근처 포켓몬센터 위치를 잘못 적은 메모 때문에 한 방향 절벽을 반복해 오가던 실행이 dreaming으로 메모를 바로잡은 뒤 Cerulean City에 도달했다.
- **위키 실험**: 인수한 소프트웨어 회사 Stainless의 내부 파일 약 35만 개(약 4억 2,000만 토큰)를 대상으로 Opus 5 에이전트가 128회 dreaming 세션을 돌려 위키를 구축했다. 25개 평가 질문의 충족 기준 비율이 13%에서 48%로 올랐고, 검색+위키는 61%로 검색 단독 53%를 앞섰다. 단, 위키가 항상 이득이 되지는 않았다.
- **범위**: Managed Agents와 Claude Code의 자동 메모리를 쓴 연구 설정 설명이지, dreaming을 일반 제품 기능으로 출시한다는 발표는 아니다. 메모리 정리는 컴퓨트를 쓰고, 정리 주기는 아직 열린 문제다. 모든 평가는 Anthropic 자체 측정으로 독립 검증이 없다.

## 왜 중요한가 (1인 개발자 관점)

1. **이 위키의 방식이 정답에 가깝다는 실증이다**: 이 위키(ai-native-mind)는 raw 소스를 모아 LLM이 위키로 정리하는 구조다. Anthropic의 실험은 바로 그 구조 — 로그를 위키로 엮으면 질문 답변이 13%에서 48%로 오른다 — 를 자사 데이터로 확인했다. "위키를 쌓는 일"이 메모리 설계의 정석 중 하나라는 뜻이다.
2. **메모리의 질이 양을 이긴다**: 413개 파일을 남긴 모델보다 9개 파일만 남긴 모델이 더 잘했다. 메모는 많이 남기는 게 아니라, 틀린 것을 고치고 필요한 것만 올리는 정리가 본질이다. 내 에이전트의 MEMORY.md도 "쌓는 것"보다 "다듬는 것"이 중요하다.
3. **"무엇을 위해"만 정하고 방법은 맡겨라**: 강한 모델에게 기록 방법을 세세히 지시하면 오히려 약해졌다는 결과는, 하네스 설계의 교훈이다. 목적과 경계만 정하고, 방법은 모델이 스스로 찾게 두는 것이 낫다. 이는 하네스 엔지니어링의 "가이드, not 스크립트" 원칙과 같다.

## 한계 (명시)

- 연구 설정 설명이지 제품 출시 발표가 아니다. dreaming이 일반 Claude 제품에 언제·어떻게 들어갈지는 미공개다.
- 모든 평가는 Anthropic 자체 측정으로, 독립 재현이나 외부 검증이 없다.
- 위키 실험은 자사 인수 회사의 내부 파일 기준이라, 다른 도메인으로의 일반화는 미검증이다. 메모리 정리의 컴퓨트 비용과 적정 주기는 열린 문제다.
