# Microsoft Agensh — 중앙 오케스트레이터 없는 1,024개 에이전트 하네스

## 쉽게 읽기

**비유**: 반장이 없는 학급이다. 보통 에이전트 팀은 반장(리드 에이전트)이 일을 나누고 합치는데, Agensh는 반장 없이 학생들끼리 칠판(공유 워크스페이스)에 '내가 이 문제 풀게'라고 적고, 끝나면 직접 합친다. 반장이 병목이 되지 않으니 학생을 1,024명까지 늘려도 돌아간다.

| 용어 | 풀이 |
|------|------|
| **하네스** | 에이전트가 도구를 쓰고, 기억하고, 협업하도록 받쳐 주는 실행 인프라 |
| **오케스트레이터** | 작업을 계획·배정·병합하는 중앙 관리자 에이전트 |
| **ProgramBench** | 큰 소프트웨어를 처음부터 재구축하는 난이도 높은 코딩 벤치 |

## 한줄 정의

2026-10-24 Microsoft Research가 오픈소스 공개한 탈중앙 다중 에이전트 하네스 — 리드 에이전트 없이 워커들이 공유 인프라를 통해 태스크 선점·공유·병합을 스스로 수행하며 1,024개까지 확장, ProgramBench에서 규모·속도 이득을 실증.

## 핵심 내용

- **조율의 이동**: 계획·배정·병합을 프롬프트가 아니라 인프라(공유 워크스페이스·메시지 인터페이스·컨텍스트 보드)로 옮김. 워커는 동일한 5단계 루프를 비동기로 반복.
- **규모**: 1→1,024개, 16노드×64개, Linux + Docker Compose. 워커당 입력 272,000토큰·출력 128,000토큰·메모리 64GiB 상한, 과제당 6시간 오프라인 예산.
- **성능**: 5개 과제 평균 19.31%(1개)→28.78%(128개). pandoc 33.89%(1개)→55.06%(1,024개, GPT-5.6-sol), GPT-6.1-sol + 32개에서 79.59%.
- **속도**: pandoc 30% 도달이 128개 30분, 32개 60분, 8개 90분 — 규모가 속도를 사는 구조.
- **창발**: 규모 증가에 따라 동료 조율→다중 통합→표준 워크플로우→역할 전문화로 협력 형태가 진화.

## 왜 중요한가 (1인 개발자 관점)

1. **복사할 것은 무리가 아니라 패턴**: 1,024개는 스턴트에 가깝고, 진짜 수확은 '선점·검증·병합 규칙을 인프라로 만든다'는 설계 전환 — 소규모 팀에도 그대로 적용된다.
2. **하네스가 병목이다**: 모델 성능보다 조율 구조가 천장을 결정한다는 실증. 에이전트 시스템을 짤 때 감독자 프롬프트부터 고치는 습관을 버릴 근거.
3. **비용은 미지수**: 토큰 비용 미공개 — 규모 실험을 그대로 따라 하면 청구서가 먼저 터질 수 있다. 작은 규모에서 단위 비용을 재는 것이 선행 과제.

## 한계 (명시)

- 벤치는 ProgramBench 5개 과제로 한정, 일반 코딩 업무로의 일반화 미검증.
- 1,024개 수치는 실험 상한이지 권장 운영 규모가 아님.
- 토큰 비용·운영 복잡도 미공개로 실전 채택 비용을 가늠하기 어려움.
