# 에이전트 길들이기: 하네스 실전 가이드 (Harness Building Blocks)

## 쉽게 읽기

**한 줄**: 하네스는 AI에게 **고삐·울타리**를 채우는 일이다. **Guides**는 출발 전에 좁혀 두는 길, **Sensors**는 결과를 보고 **틀리면 되돌리는 검사**다.

| 말 | 뜻 |
|----|-----|
| **Guides** | 시작 전 규칙·도구 범위 **좁히기** |
| **Sensors** | 린트·테스트·(필요 시) AI 심판으로 **검사** |

## 🏫 중학교 2학년 1학기 첫 수업: "야생마에 고삐와 안장 채우기"

에이전트 설계자를 꿈꾸는 여러분, 환영합니다! 
1학년 때 배운 '프롬프트'가 말에게 "저기 목적지로 가자!"라고 속삭이는 것이라면, 오늘 배울 **하네스(Harness)**는 말이 절벽으로 떨어지거나 엉뚱한 길로 새지 않게 막아주는 **고삐, 안장, 그리고 길가의 울타리**입니다.

## 한줄 설명

에이전트가 사고 치기 전에 미리 막고(Guides), 행동한 직후에 검사해서 고치게 만드는(Sensors) 구체적인 실전 코드/규칙 패턴입니다.

---

## 🚨 문제 상황: "얘가 왜 이러지?"

LLM(대규모 언어 모델)은 똑똑하지만 자유분방합니다. 오케스트레이션(지휘)을 하려면 에이전트들이 예측 가능하게 움직여야 하는데, 현실은 그렇지 않습니다.
- **포맷 무시:** JSON으로 달라고 했는데 설명글을 잔뜩 붙여서 줍니다.
- **환각(Hallucination):** 없는 라이브러리를 임포트(import)해서 코드를 짭니다.
- **무한 루프:** 에러가 나면 고치지도 못하면서 똑같은 명령어만 계속 실행합니다.

이런 상황에서 에이전트를 그냥 방치(Out of the loop)하면 대참사가 일어납니다.

---

## 🛠️ 해결 방법: 하네스의 두 가지 핵심 부품 (Guides & Sensors)

훌륭한 설계자는 "AI가 똑똑해지길 기도"하지 않습니다. 대신 **실수할 수 없는 환경(하네스)**을 만듭니다.

### 1. Guides (가이드): "시작하기 전에 미리 막기" (피드포워드)
에이전트가 행동을 시작하기 **전에** 주어지는 좁고 명확한 길(제약)입니다.

*   **실전 예시 (시스템 프롬프트 & 규칙):**
    *   **나쁜 예:** "코드를 짜줘."
    *   **좋은 예 (가이드 적용):** "코드를 짤 때는 반드시 우리 프로젝트의 `CLAUDE.md` 규칙을 먼저 읽어. 응답은 무조건 `<output>` 태그 안에 JSON 형태로만 넣어."
*   **어떻게 구현하나요?**
    *   **도구(Tool) 스키마 좁히기:** AI에게 컴퓨터 전체를 제어하는 `bash` 권한 대신, 특정 폴더 안에서만 쓸 수 있는 `safe_bash` 도구만 쥐여줍니다.
    *   **루브릭(Rubric) 제공:** "이런이런 조건을 만족해야 합격이야"라는 채점 기준표를 작업 시작 전에 미리 줍니다.

### 2. Sensors (센서): "행동 직후에 검사하고 혼내기" (피드백)
에이전트가 뭔가 결과물을 내놓았을 때, 그것이 맞는지 **자동으로 검사**하고 틀리면 다시 시키는 장치입니다.

*   **실전 예시 (자동화된 검사기):**
    *   에이전트가 코드를 짰습니다. 바로 실제 서버에 올릴까요? **절대 안 됩니다!**
    *   **센서 작동:** 에이전트가 코드를 짜면, 눈에 보이지 않는 곳에서 `npm run lint` (문법 검사)와 `npm test` (테스트 코드)가 자동으로 돌아갑니다.
*   **어떻게 구현하나요?**
    *   **Computational Sensor (계산적 센서):** 린터, 타입 체커, JSON 스키마 검증기. (빠르고 쌉니다. 컴퓨터가 0.1초 만에 틀렸다고 알려줍니다.)
    *   **Inferential Sensor (추론적 센서):** AI 심판관. "이 코드가 보안상 안전한지 검토해줘"라고 다른 AI(Evaluator)에게 물어봅니다. (조금 느리지만 복잡한 걸 잡아냅니다.)

## 🎯 적용 예시: "오케스트레이션을 위한 하네스 조립"

여러분이 나중에 에이전트 3마리를 지휘(오케스트레이션)한다고 상상해 봅시다.
1. **[코더 에이전트]**가 코드를 짭니다. **(가이드: "TypeScript만 써라")**
2. **[센서 발동!]** 코드가 완성되면 자동 테스트 도구(Sensor)가 검사합니다. 에러가 나면 에러 메시지를 통째로 [코더]에게 다시 던집니다. "다시 짜와!"
3. 테스트를 통과하면 **[리뷰어 에이전트]**라는 추론적 센서가 한 번 더 문맥을 검사합니다.
4. 모두 통과해야 비로소 작업이 끝납니다.

이것이 바로 **에이전트 = 모델(Model) + 하네스(Harness)**의 진정한 의미입니다!

---

## ⚖️ 장단점

| 장점 | 단점 |
|------|------|
| AI의 환각과 실수를 획기적으로 줄여 신뢰성(Reliability)을 높입니다. | 하네스 규칙을 너무 빡빡하게 짜면, AI가 갇혀서 창의적인 문제 해결을 못 합니다. (오버엔지니어링) |
| 인간이 일일이 확인(In-the-loop)하지 않고도 자동화가 가능해집니다. | Computational / Inferential 센서를 구축하는 데 초기 개발 시간이 많이 듭니다. |
