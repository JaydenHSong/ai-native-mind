# 오케스트레이션 패턴 실전 연습 (Orchestration Patterns)

## 쉽게 읽기

**한 줄**: 일을 **한 마리**에게 몰아주지 말고, **릴레이(체이닝)·동시에(병렬)·틀리면 다시(평가-최적화)** 중 무엇에 맞게 나눌지 고르는 연습이다.

| 패턴 | 언제 |
|------|------|
| **체이닝** | 순서가 **고정** |
| **병렬** | 덩어리 나눠 **동시에** |
| **Evaluator-Optimizer** | 품질이 **최우선** |

## 🏫 중학교 3학년 1학기: "AI 팀원들의 릴레이 달리기"

에이전트 한 마리가 모든 일을 다 하려고 하면, 결국 지치거나(토큰 한계), 실수(환각)를 하게 됩니다. 
혼자서 기획하고, 디자인하고, 코딩하고, 테스트까지 다 하는 천재는 드뭅니다. 그래서 우리는 '역할을 나눈 여러 에이전트'들을 조립하여 하나의 팀으로 움직이게 만듭니다. 이것을 **'오케스트레이션(Orchestration, 지휘)'**이라고 합니다.

## 한줄 설명

복잡한 작업을 단순하게 쪼개고, 각 단계에 전문화된 에이전트를 배치하여 릴레이(체인)나 분업(병렬)을 시키는 설계 기법입니다.

---

## 🛠️ 언제 어떤 패턴을 써야 할까? (의사결정 나무)

오케스트레이션의 6대 패턴 중, 실무에서 가장 많이 쓰이는 3가지 상황을 연습해 봅시다.

### 1. 작업 순서가 고정되어 있나요? 👉 프롬프트 체이닝 (Prompt Chaining)
가장 기본적이고 안정적인 패턴입니다. A가 끝나면 결과를 B에게 토스합니다.
*   **상황:** 영문 블로그 글을 한국어로 번역하고 요약해서 포스팅해야 합니다.
*   **설계 (릴레이 달리기):**
    1. [번역 에이전트]가 글을 초벌 번역합니다. 
    2. 결과를 [교정 에이전트]에게 넘깁니다. (어색한 문맥 수정)
    3. 교정된 결과를 [요약 에이전트]에게 넘겨 3줄 요약을 뽑아냅니다.
*   **장점:** 중간에 에러가 나면 어느 에이전트가 실수했는지 찾기 쉽습니다.

### 2. 동시에 여러 곳을 파헤쳐야 하나요? 👉 병렬 처리 (Parallelization)
시간을 단축하기 위해 하위 작업을 동시에 던지는 패턴입니다.
*   **상황:** 10만 줄짜리 코드 전체에 대해 보안 취약점을 검사해야 합니다. 한 마리가 다 읽으면 하루 종일 걸립니다.
*   **설계 (Sectioning):**
    *   코드를 10개 덩어리로 쪼갭니다.
    *   10마리의 [보안 에이전트]를 동시에(병렬로) 복제하여 출동시킵니다.
    *   결과가 다 돌아오면, [취합 에이전트(Reducer)]가 모아서 하나의 보고서로 합칩니다.
*   **장점:** 속도가 엄청나게 빠릅니다. (하지만 API 비용도 동시에 나갑니다!)

### 3. 결과물의 퀄리티가 제일 중요한가요? 👉 평가자-최적화자 (Evaluator-Optimizer)
서로 싸우면서 완벽을 기하는 '무한 피드백 루프' 패턴입니다.
*   **상황:** 버그 하나 없는 완벽한 알고리즘 코드를 짜야 합니다.
*   **설계 (PDCA 사이클):**
    1. [코더 에이전트(Optimizer)]가 코드를 짭니다.
    2. [리뷰어 에이전트(Evaluator)]가 코드를 채점하고, 틀린 부분을 매섭게 지적(Feedback)하여 돌려보냅니다.
    3. [코더 에이전트]가 지적받은 걸 고쳐서 다시 냅니다.
    4. 리뷰어가 "합격(Pass)!"을 외칠 때까지 무한 반복합니다.
*   **장점:** 인간이 개입하지 않고도 산출물 품질이 비약적으로 상승합니다. (우리 프로젝트의 Gap Analysis가 바로 이 패턴입니다!)

## 🚨 실무 주의사항: "상태(State)를 꼭 기억하세요"

에이전트들이 릴레이를 하다가 중간에 한 녀석이 뻗으면(에러) 어떻게 될까요?
처음부터 다시 시작하면 돈(API 비용)이 너무 아깝겠죠?
그래서 **'상태 기계(State Machine)'**라는 개념을 도입해, "지금 3번 에이전트가 작업 중이었고 여기까지 완료됨"이라는 **체크포인트(상태)**를 데이터베이스에 꼭 기록하면서 지휘해야 합니다.
