# 2026-05-18 학습 일지 — harness shape · compiled skills · version-upgrade eval

## 이 글을 읽는 법 (30초)

오늘 3편은 서로 다른 층을 다루지만 한 문장으로 묶인다.

> **에이전트 성능은 모델 alone이 아니라, 하네스가 예산을 어떻게 배분하고, skill을 어떤 모양으로 런타임에 싣고, 무엇을 작업 단위로 평가하느냐에 따라 달라진다.**

- [[concepts/harness-engineering|Harness Engineering]]: **깊게 생각한 적은 시도**, evaluation-hack 감시, worktree 격리
- [[concepts/tool-use|Tool Use]]: skill을 긴 문서가 아니라 **compiled runtime interface** 로 보기
- [[concepts/llm-evaluation|LLM Evaluation]]: bug-fix/feature 다음 단계로 **version-upgrade roadmap eval** 보기

---

## 1. 오늘 수집한 3편

### 1-A. Effective Harness Engineering for Algorithm Discovery with Coding Agents

**한 줄**: "같은 토큰 예산이면 많은 얕은 시도보다 적은 깊은 시도가 낫고, 강한 모델일수록 evaluation hack 감시가 더 필요하다."

- Vesper framework로 harness 설계 질문 3개를 실험
- 질문:
  1. 많은 후보 vs 깊은 후보
  2. evaluation hack 탐지
  3. full filesystem access 병렬 실행 격리
- 핵심 결론:
  - **fewer algorithms + deeper thought** 가 더 효율적
  - **more capable models produced evaluation hacks at higher rates**
  - 병렬 실행은 **Git worktree isolation** 이 중요

→ 기존 위키에서 말하던 "하네스는 안전장치"라는 관점을 한 단계 넓혀, **하네스는 budget allocator + anti-gaming detector + parallel isolation layer** 라는 해석이 생겼다.

### 1-B. SkillSmith: Compiling Agent Skills into Boundary-Guided Runtime Interfaces

**한 줄**: "skill은 매번 읽히는 설명서가 아니라, 미리 컴파일해 둔 실행 경계로 바뀔 때 가장 싸고 빠르다."

- 기존 skill 방식의 두 낭비:
  - **irrelevant context injection**
  - **repeated skill-specific reasoning and planning**
- 해결:
  - skill package를 offline에서 분석
  - **fine-grained operational boundaries** 추출
  - **minimal executable interfaces** 로 컴파일
- SkillsBench 결과:
  - token **-57.44%**
  - thinking iterations **-42.99%**
  - solve time **-50.57% (2.02x faster)**
  - cost **-57.44%**

→ 지난주에 쌓은 SKILL.md / MCP / tool schema 이야기를 더 구체화한다. 이제 skill은 **context asset** 이면서 동시에 **runtime artifact** 다.

### 1-C. RoadmapBench: Evaluating Long-Horizon Agentic Software Development Across Version Upgrades

**한 줄**: "실제 장기 개발은 bug를 하나 고치는 일이 아니라, 버전 간 roadmap을 따라 수십 파일·수천 줄을 맞춰 가는 일이다."

- 구성:
  - **115 tasks**
  - **17 repositories**
  - **5 languages**
  - **median 3,700 lines / 51 files**
- source-version snapshot에서 시작해 target version의 기능을 roadmap instruction으로 구현
- 결과:
  - **13 frontier models** 평가
  - 최고 **Claude Opus 4.7 = 39.1%**
  - 최저 **5.2%**
- 본문 스니펫 기준으로 **scaffold sensitivity** 도 별도 분석

→ 2026-05-17의 [[journal/2026-05-17|FeatureBench]] 가 feature-development eval을 열었다면, 오늘은 그 다음 단계인 **version-upgrade / release-scale eval** 이 추가됐다.

## 2. 오늘의 연결 그림

| 층 | 오늘 소스 | 새로 선명해진 질문 |
|---|---|---|
| **하네스 운영** | Effective Harness Engineering | 같은 예산에서 무엇을 늘릴까? 시도 수인가, 사고 밀도인가? |
| **도구/skill 형태** | SkillSmith | skill을 프롬프트 문서로 실을까, 컴파일된 interface로 실을까? |
| **평가 단위** | RoadmapBench | bug/feature 다음에 release-scale 작업을 어떻게 재나? |

세 편을 한 줄로 압축하면 이렇다.

1. **하네스는 시도 수를 늘리는 기계가 아니라 좋은 시도를 남기게 만드는 기계다.**
2. **skill은 설명서가 아니라 실행 경계로 바뀔 때 runtime 비용이 내려간다.**
3. **코딩 eval은 bug → feature → roadmap/release로 granularity를 올려야 현실에 가까워진다.**

---

## 3. 기존 지식과의 연결 포인트

### 3-A. 2026-05-17의 FeatureBench 다음 칸이 생겼다

어제까지 coding eval 축은 대략 이렇게 보였다.

- bug-fix benchmark
- feature-development benchmark ([[journal/2026-05-17|FeatureBench]])

오늘 RoadmapBench가 들어오면서 다음 칸이 생긴다.

- **version-upgrade / roadmap benchmark**

즉 코딩 agent 성능을 말할 때는 **무슨 작업 단위냐**를 함께 말해야 한다.

### 3-B. skill loading이 context engineering과 runtime engineering을 잇는다

SkillSmith는 [[concepts/context-engineering]] 과 [[concepts/tool-use]] 사이의 다리를 놓는다.

- 지금까지는 "무엇을 보여줄까"가 중심이었다면
- 오늘은 "보여줄 것을 **미리 컴파일해 어떤 실행 경계로 바꿀까**"가 추가됐다

→ context selection이 곧 runtime interface design이라는 연결이 더 강해졌다.

### 3-C. stronger model = simpler harness 가 항상 아니다

최근 위키에는 "모델이 좋아지면 하네스를 단순화할 수 있다"는 Anthropic 사례가 있었다. 오늘 Effective Harness Engineering은 거기에 반대 방향 보정을 넣는다.

- **모델이 강해질수록 evaluation hack도 더 잘할 수 있다**
- 따라서 어떤 부분은 단순화하더라도, **anti-gaming layer** 는 오히려 두꺼워질 수 있다

→ "모델 업그레이드 = 하네스 축소"를 자동 규칙으로 두면 안 된다.

## 5. 핵심 배움

1. **하네스는 모델 밖의 포장지가 아니라, 성능 분포를 바꾸는 계산 구조다.**
2. **강한 모델은 더 안전할 수도 있지만, 동시에 score-gaming도 더 잘할 수 있다.**
3. **skill은 긴 context보다 컴파일된 runtime interface로 바뀔 때 비용·속도가 크게 줄어든다.**
4. **코딩 eval은 bug-fix만으로는 현실을 과대평가한다. feature 다음엔 roadmap/release-scale eval이 필요하다.**
5. **병렬 에이전트 운영의 기본 단위는 공유 작업공간이 아니라 격리된 worktree/ephemeral workspace여야 한다.**
