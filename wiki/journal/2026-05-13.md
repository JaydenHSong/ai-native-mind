# 2026-05-13 학습 일지 — 수요 데일리: Verification-Gated Action, 3-도메인

## 이 글을 읽는 법 (30초)

어제(2026-05-12)는 **"모델 아래 세 레버"**(workflow 입구 / eval 뒤 / invocation 위)였다. 오늘 자동 인제스트 3편은 그 정신을 한 칸 더 끌어내려 **"출력 직전 — committing 전의 verification gate"**를 도메인별로 답한다.

| 도메인 | 질문 | 논문 |
|---|---|---|
| **Text / Claim** | 멀티 에이전트 보고서의 claim을 어떻게 typed하게 검증·게이팅하나? | Kamelhar (Oracle), "GSAR: Typed Grounding..." ([arXiv:2604.23366](https://arxiv.org/abs/2604.23366), 2026-04-25) |
| **Code** | Cross-language vulnerability를 고치기 *전에* 무엇을 verify해야 하나? | Gajjar (GWU), "Verify Before You Fix" ([arXiv:2604.10800v1](https://arxiv.org/abs/2604.10800v1), 2026-04-12) |
| **Embodied / Visual** | Open-world scene에서 다음 skill을 부르기 전 evidence가 충분한지 어떻게 판단하나? | "Affordance Agent Harness: Verification-Gated Skill Orchestration" ([arXiv:2605.00663](https://arxiv.org/abs/2605.00663), 2026-05-01) |

## 한 그림으로 잇기

```
       Model / Skill 출력 (probabilistic)
                 │
                 ▼
        ┌────────────────────┐
        │  Evidence Store    │   증거를 typed하게 누적
        └─────────┬──────────┘
                  ▼
        ┌────────────────────┐
        │  Verifier (도메인별) │
        │  - GSAR: 4-way + asym penalty
        │  - VBYF: execution sandbox
        │  - A-Harness: relative + actionable diagnostic
        └─────────┬──────────┘
                  ▼
        proceed │ regenerate │ replan   ← 3-tier decision
                  │
                  ▼
        bounded budget retry → 안 되면 escalate
```

세 시스템 모두 같은 구조다. **다른 것은 evidence의 종류**:

| 도메인 | Evidence | 게이트 핵심 |
|---|---|---|
| Text | Wikipedia gold evidence + claim typology | Weighted score + asymmetric contradiction penalty |
| Code | Execution trace (exploit 재현 여부) | Strict invariant: "no repair without execution-confirmed exploitability" |
| Embodied | Skill outputs + episodic prior | "무엇이 missing인지" 진단 (actionable diagnostic) |

## 각 편 한 줄

### (1) GSAR — "Binary groundedness는 부족하다, claim을 4타입으로 잘라라"

Oracle의 Kamelhar가 FEVER + gold Wikipedia evidence로 검증한 framework. Claim을 **Grounded / Ungrounded / Contradicted / Complementary** 4가지로 partition, evidence type에 weight 차등, **asymmetric contradiction penalty**(모순 claim 하나가 grounded claim 여럿을 무력화)를 코어로 두고, 점수에 따라 *proceed / regenerate / replan* 3-tier로 분기.

**정량 (4 LLM judge: gpt-5.4 / sonnet-4-6 / opus-4-7 / gemini-2.5-pro)**:

- GSAR default **100 proceed** vs binary baseline **35** → **+185% grounded-output rate**
- Weighted: proceed rate 16/50 → 18/50 (+4pp)
- **Ablation**: contradiction penalty 제거 시 contradicted claim 포함 보고서가 advance — penalty 존재 이유 입증
- 알고리즘에 대해 **6 structural properties proof** (단순 heuristic 아님)

어제 [[journal/2026-05-12|JRH]]가 "judge가 universally reliable하지 않다"였다면, GSAR는 *"그 unreliable judge 4명을 4-way typology + 합의로 어떻게 묶어 게이트로 만드나"*의 짝.

### (2) Verify Before You Fix — "Repair는 execution이 confirm한 vulnerability에만"

GWU의 Gajjar가 Java/Python/C++ cross-language vulnerability 파이프라인에 박은 strict invariant. 3-stage:

1. **Hybrid Structural-Semantic Detection** — uAST(Universal AST)로 3 언어 normalize, GraphSAGE + Qwen2.5-Coder-1.5B embedding two-way gating
2. **Execution-Grounded Validation** — 후보를 실제 실행해 exploit 가능성 확인
3. **Validation-Aware Iterative Repair** — confirm된 것만 repair, repair 결과도 execution으로 verify

핵심 framing — **probabilistic inference ≠ verified conclusion**. 학습된 classifier의 확률 출력을 verify 없이 행동으로 옮기면 *compounding failure*가 누적.

본 위키의 [[patterns/ai-code-review|ai-code-review]] Plan-Review-Execute에 **Execute 직전 execution gate**를 한 칸 추가하는 자연스러운 변형.

### (3) Affordance Agent Harness — "Fixed pipeline 대신 evidence-driven adaptive runtime"

2026-05-01 arXiv. Affordance grounding(open-world에서 "어디·어떻게 interact할지") 도메인. 최근 시스템들이 detection / segmentation / interaction-imagination 같은 heterogeneous skill을 결합하지만 **fixed pipeline**으로 묶어서 per-instance difficulty에 못 맞춤. A-Harness는:

| 컴포넌트 | 역할 |
|---|---|
| **Evidence Store** | Skill outputs 누적·구조화 |
| **Router** | Adaptive하게 다음 skill 선택·parameterize |
| **Episodic Memory** | 반복 카테고리에 prior 제공 |
| **Verification Gate** | Relative + **actionable** diagnostic ("무엇이 missing"까지) |
| **Cost Control** | Bounded inference cost |

차별점 — 검증 출력이 단순 score가 아니라 **"무엇이 missing인지를 명시해 다음 액션을 유도"**한다. 단순 "score<threshold → retry"보다 한 단계 위.

> **주의**: 본문 정독 미완 (WebFetch rate limit). 정확한 정량 결과는 후속 데일리에서 확인 필요. raw 파일 frontmatter에 명시.

## 합류점 — Convergence

세 편이 한 문장으로 묶인다: **"Probabilistic inference를 행동으로 옮기기 전에, 도메인에 맞는 evidence로 verify해라."** 도메인이 text → code → embodied로 바뀌어도 구조는 같다.

지난 시점들과 합치면 1년 그림이 더 또렷해진다:

| 시점 | 라인 | 무엇이 잠겼나 |
|---|---|---|
| 2026-05-06 AM | 자동 진화 (Last Harness / AHE / Meta-Harness) | H가 *진화*하는 통로 — 똑똑함 증가 |
| 2026-05-06 PM | 결정적 잠금 (CAAF) | H 자체를 incorruptible asset으로 잠금 |
| 2026-05-12 | 모델 아래 3 layer (MEP / JRH / GROUNDING.md) | workflow 입구 / eval 뒤 / invocation 위 |
| **2026-05-13** | **출력 직전 게이트 (GSAR / VBYF / A-Harness)** | **commit 직전, 도메인별 verifier** |

**축**이 잡힌다 — *진화 라인은 위로 올라가고*, *잠금 라인은 아래로 내려간다*. 잠금 라인이 이제 **출력 단계까지** 도달했다. 1인 개발자에게 의미하는 바는 "에이전트 fancy하게 만드는 것보다, *commit 전 verifier를 도메인에 맞게 설계*하는 것이 ROI가 높아진다"는 것.

또 다른 관찰 — **GSAR가 4 judge를 같이 굴린다**는 점은 어제 JRH가 보여 준 "judge 자체가 unreliable" 결과의 자연스러운 운영적 대응이다. 단일 judge → multi-judge typed consensus로의 시프트.

1. **세 후보 선택 — 왜 이 3편?**
   - 어제 일지에 명시된 다음 후보 풀: GSAR / Verify Before You Fix / Agentic AI Comprehensive Survey (arXiv 2510.25445).
   - Survey는 어제 일지에 명시된 대로 *금요 weekly review*용 자료라 오늘은 제외.
   - 대신 fresh May 2026 source인 **Affordance Agent Harness (arXiv 2605.00663, 2026-05-01)**를 추가 — 이유: 텍스트(GSAR) + 코드(VBYF) 도메인만으론 *"verification-gated"* 주제의 generalizability가 부족했다. Embodied 도메인이 들어와야 "도메인 무관 원리"임이 드러난다.
   - 선정 기준 — (a) 위키 빈 자리(harness 케이스북의 embodied 칸, hallucination 페이지의 grounding 메커니즘, ai-code-review의 execution gate)를 채우는가, (b) 다른 두 편과 *공통 주제*를 형성하는가, (c) *정량 데이터*가 있는가.

2. **add-only 원칙 유지** — 기존 본문·링크 손대지 않음. frontmatter `sources`/`updated`/`tags`만 갱신. [[journal/2026-05-12]] 선례 따름.

3. **신규 페이지 vs 보강** — verification-gated harness 패턴 페이지를 *신설하지 않고* concepts/harness-engineering의 섹션으로만 흡수. 이유: 3 도메인 사례뿐이라 일반 패턴화는 이르다. 다음 ingest에서 *4번째 도메인*(예: financial/legal/medical)이 같은 구조로 나오면 그때 별도 페이지 검토.

## Self-declared prediction (오늘 ingest의 falsifiable claim)

> **다음 데일리(또는 그 다음) 안에, "verification gate" 또는 "verify-before-action"이라는 표현이 *코드 도메인이 아닌* agent 시스템 글(예: text agent, customer-support agent, research agent)에서 표준 패턴 어휘로 등장한다.** 근거 — 오늘 3편이 서로 다른 학회·도메인에서 같은 구조를 동시에 제시했다는 점은 *이미 community 의미장에 임계점*이 왔다는 신호. 코드 도메인에서 시작된 "test before commit"이 다른 도메인에 일반화된다면 *2025년 RAG가 그랬듯이* 어휘가 빠르게 표준화된다. 빗나가면 → 오늘 3편의 합류는 *우연*이었고, 도메인 간 verification 어휘 통일은 아직 멀었다는 뜻. 다음 데일리에서 검증.
