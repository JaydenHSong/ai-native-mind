# 2026-05-02 학습 일지 — 멀티 에이전트의 정량 한계 + 6 레버 + 3-에이전트 분리

## 이 글을 읽는 법 (30초)

토요일 데일리 인제스트. AI 에이전트 엔지니어링에 관한 세 글을 raw에 정리하고, 위키의 `harness-engineering`, `ai-orchestration`, `subagents-delegation` 페이지에 **추가만** 했다. 기존 본문·링크는 건드리지 않았다.

세 글을 한 그림으로 묶으면 이렇다.

- **Google**: "에이전트 많을수록 좋다"는 통념을 180개 컨피그 통제 실험으로 반박. **태스크 속성에 코디네이션 구조를 정렬**하라.
- **Anthropic (InfoQ 정리)**: 장시간 자율 코딩은 **Planner / Generator / Evaluator** 3-에이전트로 분리. self-eval은 양성 편향이라 별도 evaluator가 핵심 레버.
- **HumanLayer**: 모델은 똑똑해질수록 **새 방식으로 실패**한다. 컨피그 6 레버(CLAUDE.md / MCP / Skills / Sub-agents / Hooks / Back-pressure)로 실전을 받치라.

## 오늘 배운 것 (3개 소스)

- **[Towards a Science of Scaling Agent Systems — Google Research / arXiv 2512.08296 (2026-01-28)](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)** — 5 아키텍처(Single / Independent / Centralized / Decentralized / Hybrid) × 3 모델 패밀리(GPT / Gemini / Claude) × 4 벤치마크(Finance-Agent / BrowseComp-Plus / PlanCraft / Workbench) = **180 컨피그**. 핵심 결과: parallelizable 태스크에서 Centralized는 단일 에이전트 대비 **+80.9%**, 그러나 순차 태스크(PlanCraft)는 모든 멀티 변형이 **-39 ~ -70%**. 신뢰성 측면에서 Independent는 오류 증폭 **17.2x**, Centralized는 **4.4x** — 즉 오케스트레이터는 성능 booster가 아니라 **validation bottleneck = 안전 컴포넌트**다. 도구 ≥ 16개에서 코디네이션 세금이 비례 이상으로 증가하는 "tool-coordination trade-off"도 별도 신호. R²=0.513 회귀로 87% 미관찰 태스크에서 최적 코디네이션 전략 적중. 이 데이터가 Anthropic의 "단순하게 시작 → 평가 → 안 되면 멀티" 원칙을 정량으로 떠받친다.

- **[Anthropic Designs Three-Agent Harness — InfoQ (2026-04-04)](https://www.infoq.com/news/2026/04/anthropic-three-agent-harness-ai/)** (1차 출처: [Anthropic Engineering — Harness Design for Long-Running Apps](https://www.anthropic.com/engineering/harness-design-long-running-apps)) — 수 시간짜리 자율 코딩·프론트엔드 디자인 세션의 **컨텍스트 손실·조기 종료**를 푸는 패턴. **Planner**(JSON feature spec, init script, 워킹 앱 스켈레톤) → **Generator**(한 번에 한 feature, 매 세션 컨텍스트 리셋, commit-by-commit) → **Evaluator**(별도 모델·few-shot 채점, Playwright MCP로 라이브 페이지 직접 운전, 4축 채점: design quality / originality / craft / functionality). 사이클 당 5~15회 반복, run당 최대 4시간. 핵심 인용: "Separating the agent doing the work from the agent judging it"(12단어). compaction 대신 **컨텍스트 리셋 + 구조화 핸드오프 아티팩트**를 쓰는 게 모델이 컨텍스트 한계 근처에서 보수적으로 변하는 것을 막는다.

- **[Skill Issue: Harness Engineering for Coding Agents — HumanLayer (Kyle, 2026-03-12)](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents)** — 1년치 코딩 에이전트 운영 끝에 정리한 6 레버. (1) **CLAUDE.md/AGENTS.md** 60줄 미만 + progressive disclosure(ETH Zurich 138-agentfile 연구가 LLM 생성 파일은 +20% 비용·성능 저하 확인). (2) **MCP**는 도구를 위한 것 — 학습 데이터에 잘 표현된 CLI(GitHub/Docker/DB)는 MCP 대신 CLI로. (3) **Skills**는 progressive disclosure + 레지스트리는 npm install처럼 의심(ClawHavoc 인용). (4) **Sub-agents**는 역할 분류가 아니라 **context firewall** — 부모는 프롬프트와 최종 결과만, Chroma context rot 연구가 distractor는 길수록 더 해롭다고 실증. (5) **Hooks**는 git hooks의 에이전트 버전 — 성공은 침묵, 실패만 verbose, exit 2로 하네스가 다시 깨움. (6) **Back-pressure**(typecheck/test/playwright)를 컨텍스트 효율적으로 — 통과 4,000줄을 컨텍스트에 쏟지 마라. 짧은 인용(14단어): "The next time your coding agent isn't performing the way you expect, [...] check the harness."

## 인사이트

세 글이 **같은 결론을 다른 각도에서** 말한다.

- Google은 **데이터로**: 코디네이션 구조를 잘못 고르면 -70%, 잘 고르면 +81%. 디폴트는 단일 에이전트, 멀티는 분해 가능성·도구 밀도·검증자 유무를 점검한 후에.
- Anthropic은 **장시간 세션의 실전으로**: 생성과 평가가 같은 에이전트면 self-eval이 양성 편향으로 무너지니까 **분리**하라. 이게 Google의 "오케스트레이터 = 4.4x 안전 컴포넌트"와 같은 메시지다.
- HumanLayer는 **운영자의 시선으로**: 컨피그 6 레버 중 가장 큰 ROI는 **back-pressure(자기 검증)**, 그다음이 **sub-agent를 context firewall로 쓰는 것**, 그다음이 **CLAUDE.md를 60줄 미만으로 유지하는 것**.

위키 입장에서 가장 큰 변화는 [[concepts/harness-engineering]]에 마침내 **정량 근거**가 들어왔다는 점. 지금까지 "오케스트레이터를 두면 좋다"는 정성적 주장이었는데, 이제 4.4x vs 17.2x 오류 증폭 비교를 인용할 수 있다.
