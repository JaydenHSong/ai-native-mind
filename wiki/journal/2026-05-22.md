# 2026-05-22 학습 일지 — code substrate · memory scale boundary · benchmark disclosure

## 이 글을 읽는 법 (30초)

오늘 3편은 서로 다른 주제를 다루지만, 한 줄로 묶으면 이렇다.

> **agent engineering은 점점 더 "모델이 무엇을 했는가"보다, 그것이 어떤 code substrate 위에서 작동했고, memory가 얼마나 커질 때까지 usable하며, benchmark 결과가 어떤 실행 맥락을 공개했는가"를 묻는 방향으로 이동한다.**

- [[concepts/harness-engineering|Harness Engineering]]: code를 단순 output이 아니라 runtime substrate로 보는 시야가 선명해졌다.
- [[concepts/ai-memory-systems|AI Memory Systems]]: memory는 retrieval accuracy만이 아니라 **규모 증가 아래 usable evidence 유지**로 평가해야 한다.
- [[concepts/llm-evaluation|LLM Evaluation]]: benchmark score를 읽기 전에 **run disclosure quality** 를 감사해야 한다.

---

## 1. 오늘 수집한 3편

### 1-A. Code as Agent Harness

**한 줄**: "코드는 agent가 쓰는 결과물이면서 동시에, agent가 생각하고 행동하고 검증하는 하네스다."

- framing:
  - code = output only 가 아니라 **operational substrate**
  - reasoning / action / environment modeling / execution-based verification를 연결
- 3-layer survey frame:
  1. **harness interface**
  2. **harness mechanisms** (planning / memory / tool use / feedback control)
  3. **multi-agent scaling** (shared artifact / review / verification)
- 핵심 시사점:
  - planning·memory·tool use를 separate feature가 아니라 **code-backed harness mechanisms** 로 묶어 보게 만든다.
  - multi-agent coordination의 매개를 **message** 보다 **shared file / diff / test harness** 쪽으로 이동시킨다.

### 1-B. Scale-Conditioned Evaluation of Agent Memory

**한 줄**: "메모리는 지금 잘 찾느냐보다, irrelevant session이 계속 쌓여도 필요한 증거를 예산 안에서 계속 꺼낼 수 있느냐로 봐야 한다."

- 문제 설정:
  - query마다 task evidence는 고정
  - irrelevant session만 점진적으로 추가
- 4 diagnostics:
  - **budget-compliant reliability**
  - **tail memory-call burden**
  - **failure-regime decomposition**
  - **usable-scale boundary**
- 핵심 발견:
  - **HippoRAG** 는 two-call budget을 지키지만 irrelevant session 증가 시 **16~20pp reliability 하락**
  - **LiCoMemory** 는 agent 의존성이 커서, Qwen3-8B는 budget 초과, Qwen3-32B / 235B는 상대적으로 안정

### 1-C. Benchmark Disclosure Audit

**한 줄**: "벤치마크 점수보다 먼저, 그 점수가 어떤 하네스와 어떤 설정에서 나온 것인지 논문이 얼마나 공개하는지 재야 한다."

- audit schema 5 fields:
  1. **benchmark identity**
  2. **harness specification**
  3. **inference settings**
  4. **cost reporting**
  5. **failure breakdown**
- pilot audit 결과:
  - **agent benchmark papers 평균 0.38 / 1.0**
  - **classical static benchmark papers 평균 0.66 / 1.0**
  - 큰 공백은 **cost** 와 **harness spec**
- 핵심 시사점:
  - 같은 model name 결과 비교가 자주 흐려지는 이유를 **불충분한 run disclosure** 에서 찾는다.

## 2. 오늘의 연결 그림

| 층 | 오늘 소스 | 새로 선명해진 질문 |
|---|---|---|
| **runtime substrate** | Code as Agent Harness | agent capability는 어떤 code artifact 위에서 구현·검증되는가? |
| **scaling boundary** | Scale-Conditioned Memory Eval | memory store가 커질수록 증거가 언제부터 안 쓰이기 시작하는가? |
| **evaluation metadata** | Benchmark Disclosure Audit | benchmark score의 실행 맥락이 충분히 공개되어 있는가? |

세 편을 같이 보면, 최근 위키의 관심사가 다음처럼 내려간다.

1. **결과물**만 보는 것에서 **substrate** 를 보는 쪽으로
2. **현재 성능**만 보는 것에서 **규모 증가 조건** 을 보는 쪽으로
3. **점수**만 보는 것에서 **그 점수가 나온 실행 메타데이터** 를 보는 쪽으로

## 3. 기존 지식과의 연결 포인트

### 3-A. Harness Engineering 최근 축을 Code as Agent Harness가 상위 프레임으로 묶는다

최근 며칠의 흐름은 아래처럼 조각나 있었다.

- [[concepts/tool-use]] = capability object / runtime interface
- [[concepts/ai-memory-systems]] = belief / lifecycle / safety / enforcement
- [[concepts/llm-evaluation]] = spec truth / process quality / environment realism
- [[concepts/ai-orchestration]] = delegation / handoff / shared workflow

오늘 Code as Agent Harness가 들어오면서, 이 네 줄이 모두 **code-backed harness mechanisms** 라는 상위 설명으로 묶인다.

### 3-B. memory는 taxonomy 다음 단계로 "scale boundary" 질문이 추가됐다

기존 memory taxonomy는 크게 이랬다.

- 무엇을 얼마나 믿나? → BeliefMem
- 언제 압축·망각하나? → Human-Inspired Memory
- 무엇을 안 잊어야 안전한가? → MAGE
- 어떻게 절대 안 잃게 강제하나? → ClawVM

오늘 논문은 여기에 다음 질문을 추가한다.

- **얼마나 커져도 계속 쓸 만한가?** → Scale-Conditioned Evaluation

즉 memory는 구조와 update rule뿐 아니라 **성장 조건부 usability** 까지 포함해서 봐야 한다.

### 3-C. eval은 이제 quality metric만이 아니라 disclosure quality도 가져야 한다

최근 eval 계보는 다음처럼 깊어졌다.

- JRH = judge reliability
- ResearchArena / SpecBench = surface vs truth gap
- ProcBench / HarnessAudit = process controllability / trajectory audit
- WildClawBench = environment realism

오늘 disclosure audit이 들어오면서, 이 모든 것 아래에 **run disclosure layer** 가 깔린다.

즉 앞으로는 "무슨 benchmark를 썼나"만이 아니라,

- 어떤 scaffold였는가
- 어떤 evaluator version이었는가
- 비용은 얼마였는가
- 실패 breakdown은 무엇이었는가

까지 기록해야 비교가 성립한다.

## 5. 핵심 배움

1. **code는 agent가 생산하는 결과물이면서 동시에 agent runtime 자체일 수 있다.**
2. **memory 평가는 retrieval accuracy보다 growth-under-noise 조건에서의 usability를 더 강하게 물어야 한다.**
3. **usable-scale boundary는 memory 시스템의 실전 한계를 말해 주는 운영형 지표다.**
4. **benchmark 점수는 harness / evaluator / cost / failure metadata 없이 읽으면 해석력이 크게 떨어진다.**
5. **최근 agent eval은 judge → disclosure → truth → process → environment의 다층 구조로 두꺼워지고 있다.**
6. **shared artifact 설계는 멀티 agent coordination의 핵심이며, 단순 role prompt보다 load-bearing할 수 있다.**

### 9-B. 이번 주 실제 중복은 "같은 주제를 다른 경계 이름으로 반복한 것"이었다

이번 주 source들은 겉으로는 memory·eval·orchestration·security로 흩어져 있었지만, 실제로는 다음처럼 **boundary design** 질문으로 수렴했다.

- **memory boundary**: 무엇을 얼마나 믿나, 언제 잊나, 얼마나 커져도 usable한가, runtime이 어떻게 안 잃게 강제하나
- **control boundary**: 어디까지 자동 승인하고 어디서 사람에게 넘기나
- **handoff boundary**: 누구에게 무엇을 어떤 shared artifact로 넘기나
- **evaluation boundary**: 점수만 볼지, process/control/disclosure까지 볼지
- **representation boundary**: code / skill / policy 문서를 어떤 실행 artifact로 다룰지

즉 페이지를 삭제할 정도의 중복은 아니었고, **서로 다른 경계 질문을 같은 이름(memory, eval, orchestration) 아래에 넣으면서 생긴 겹침**이 더 컸다.

### 9-C. 이번 주 압축 방식

삭제 대신 다음 방식으로 압축했다.

1. [[comparisons/agent-memory-taxonomy]] 를 갱신해
   - 기존 **task / belief / lifecycle / safety** 역할 분류를 유지하고
   - 그 위에 **scale boundary / runtime enforcement / action-time safety check** 경계 질문을 덧댔다.
2. 이 일지에 주간 리뷰를 추가해, 최근 6일의 journal을 다시 읽을 때 **어떤 주제가 어디서 갈라졌는지**를 한 번에 볼 수 있게 했다.
3. 기존 concept 페이지의 세부 설명은 그대로 두고, 비교·상위 naming은 comparison/journal 쪽에 몰아 **중복 삭제 없이 해석 층만 추가**했다.

### 9-D. 삭제하지 않고 남긴 것

- **BeliefMem / Human-Inspired Memory / MAGE / ClawVM / Scale-Conditioned Eval** 세부 설명은 각 원래 페이지에 남긴다.
- raw source 경로와 핵심 수치(예: GroupMemBench 46.0%, FeatureBench 11.0%, HarnessAudit 0.32, SpecBench code size 10x당 gap +28 points)는 기존 concept/journal에서 유지한다.
- 비교 페이지는 세부 내용을 대체하지 않고, **어느 페이지가 어떤 역할을 맡는지 알려 주는 라우팅 레이어**만 담당한다.

### 9-E. 이번 주의 압축 결론

이번 주의 핵심 변화는 새 논문이 많이 들어왔다는 사실보다, **agent engineering의 병목이 모델 성능이 아니라 경계 설계 문제로 더 또렷해졌다는 점**이다.

- memory는 한 기능이 아니라 **역할 축 + 경계 축**으로 쪼개진다
- eval은 정답률이 아니라 **truth / control / disclosure / environment** 층으로 두꺼워진다
- orchestration은 단순 분업이 아니라 **handoff contract** 설계가 된다
- tool/skill은 설명서가 아니라 **runtime capability object** 쪽으로 이동한다
- safety는 refusal text가 아니라 **state diff + trajectory memory** 쪽으로 이동한다

이렇게 읽으면 이번 주 페이지들은 서로 반복이 아니라, **같은 시스템의 다른 경계면을 점점 더 잘게 분리한 기록**으로 보인다.
